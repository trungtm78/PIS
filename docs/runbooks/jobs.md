# Runbook: scheduled jobs

Stories: ST-ADM-001, ST-ADM-002. Code: `packages/kernel/src/scheduler.ts` (port and timer adapter),
`packages/db/src/job-runner.ts` (lock, history, alert), `packages/db/src/jobs.ts` (the jobs).

## The jobs

| Job | Interval | What it does | Runs in |
|---|---|---|---|
| `audit-seal` | 5 minutes | seals the new audit rows of every tenant into a chained Merkle window | API process (workers) or command line |
| `audit-verify` | hourly | walks every seal chain; a broken window raises `AUDIT_CHAIN_BROKEN`, then the job itself fails. Each tenant's verdict is kept in `audit_seal_check` and shown by ADM-11 (`BROKEN`, `STALE` after three missed runs, `UNKNOWN`, `OK`; `docs/runbooks/audit-export.md`) | API process (workers) or command line |
| `outbox-relay` | 5 seconds | one relay batch; raises `OUTBOX_LAG` and `OUTBOX_EVENT_DEAD` | API process only (it owns the broker adapter) |
| `idempotency-purge` | hourly | deletes expired idempotency rows that no legal hold contains | API process or command line |
| `certificate-expiry` | daily | marks the signing certificates whose validity has ended as `Expired` in every tenant (reads already report them as Expired; the 30-day warning of ADM-08 is computed when the register is read) | API process only |
| `master-baseline-sync` | every 6 hours | applies the signed baseline pack of the platform to each tenant: the funding source tree with the national target programmes inside their budget source, sectors, project groups, types and stages, decision types and authorities, and the rule data (national code, group thresholds, appraisal criteria) flagged with the confirmation they wait for (ST-MDM-003). The digest of the pack is verified first; an entry the tenant already has is left alone, a newer version of an entry is added without rewriting the older one; the pass is idempotent | API process only |
| `master-activation` | hourly | puts the master data versions whose date has come in force, retires the records whose retirement date has come, and sets `mdm_change_pending_gauge` to the number of change requests that wait for a reviewer in all tenants (ST-MDM-001; the pass is idempotent) | API process only |
| `dis-period-autoclose` | every 15 minutes | soft-closes the reporting periods whose deadline has passed and locks the soft-closed ones three working days after the deadline (D03 assumption, counted on the published working calendar `WORKDAY_VN`), by the same moves as the commands `softCloseReportingPeriod` and `lockReportingPeriod`, with the same audit row and event (`period.soft_closed.v1`, `period.locked.v1`) and the counter `dis_period_transition_total{to, trigger}`. A period a command is acting on at that moment is left to the next run; a soft-closed period whose year has no published working calendar stays soft closed until one exists (ST-DIS-001; the pass is idempotent) | API process only |
| `dis-reopen-expiry` | every 5 minutes | stores the end of the reopening windows of locked reporting periods: an approved `period_reopen` whose `window_until` has passed becomes `EXPIRED` (version raised by one) and leaves the audit row `dis.period_reopen_expired` (reason code `AUTO_REOPEN_WINDOW_ENDED`, the requester, the approver and the window in the diff) and the counter `dis_period_reopen_total{outcome=expired}`. **The job is the memory of the expiry, not the rule**: the window is judged by the clock everywhere it matters, so a run that is late, skipped or failed changes what is stored, never who may submit. The submit guard (`DisPeriodStore.judge`) lets a report into a locked period only while `decided_at <= now < window_until` for the approved reopening that names the project (or the whole period), and the reads of DIS-14 and DIS-22 show an elapsed window as `EXPIRED` from its last instant. Why a job at all and not only the lazy rule: the history of a request must end with a stored, audited fact (retention 10 years, reports and audits name the request later), and the table is then the same for a reader that does not run the clock logic (reports, exports, BI). A request a command is deciding at that moment is left to the next run (`for update skip locked`); the period itself is never written (ST-DIS-002; the pass is idempotent) | API process only |
| `dgv-quality-run` | every 10 seconds | executes the data quality runs that are waiting (`quality_run` in `RUNNING`, oldest first, 20 per tenant per pass): measures the approved rule versions the run names over the rows of the one frozen snapshot it names, writes the results, the verdict, the incidents of the failed rules, the audit row and the events `dgv.quality_run.completed.v1` / `dgv.incident.opened.v1` in one transaction, and sets the gauge `dgv_not_assessed_datasets_gauge`. A run is executed once (`for update skip locked`); a run that throws is taken up again by the next pass and finishes `FAILED / EXECUTION_FAILED` after five attempts; a snapshot that is no longer the frozen one that was asked for finishes it `FAILED / SNAPSHOT_CHANGED`. See docs/dgv-quality-runs.md (ST-DGV-002) | API process only |
| `retention-purge` | hourly tick, works in the 01:00 hour of Vietnam time only | the nightly retention run of each tenant (ST-ADM-017): removes technical data that has outlived its period (published outbox events 30 days, inbox payloads 90 days and metadata 2 years, sessions 180 days, delivery attempts 365 days, expired idempotency keys) and puts expired business records on the review list `retention_review_item` without ever deleting them. A record a legal hold contains is skipped. A tenant policy can only lengthen a period. Runbook: `docs/runbooks/retention.md`; gauges `retention_purged_rows`, `retention_review_listed_rows`, `retention_skipped_held_rows`, `retention_review_pending_gauge`; the pass is idempotent | API process only |
| `guarantee-expiry` | hourly tick, works in the 06:00 hour of Vietnam time only | the daily pass over the guarantees of each tenant (ST-CTR-003, CTR 3.5): an ACTIVE guarantee that is 30, 15, 7 or 0 calendar days from its expiry (in Vietnam) gets one reminder per threshold (`ctr.guarantee.expiring.v1`, turned into in-app notifications by the notification core and remembered in `last_alert_days`, so a second pass the same day sends nothing); the day after its expiry it becomes EXPIRED once (`ctr.guarantee.expired.v1`, which the issue intake of ISS answers with one issue when an advance is still owed). It never renews or extends a guarantee. Gauges `ctr_guarantee_expiring{days}` and `ctr_advance_guarantee_at_risk` (alert `CTR_ADVANCE_GUARANTEE_AT_RISK`); the pass is idempotent | API process only |
| `revision-effective` | hourly tick, at every hour | the pass over the revisions of the contracts of each tenant that wait for their day (ST-CTR-007, CTR 3.3 step 5, BR-CTR-03): a revision PENDING_EFFECTIVE whose first day (in Vietnam) has come takes over from the revision in force, which becomes SUPERSEDED and ends where the new one begins; `contract_value_vnd` and `current_revision_id` follow, the audit row `contract.revision_effective` is written and `ctr.commitment.changed.v1` tells the capital the value to commit. Revisions take over one after the other in the order of their days, so a night that was missed is made good by the next tick (the spec says once at 00:05; the pass is idempotent and an hourly tick is the same on a normal day). A revision of a contract that is no longer being performed, or whose value is below what was accepted or paid since the approval, waits. Gauge `ctr_revision_overdue` (the pending revisions more than a day late; alert `CTR_REVISION_OVERDUE`); the pass is idempotent | API process only |
| `petition-due` | hourly tick, at every hour | the pass over the petitions of contractors of each tenant that wait for an answer (ST-BID-007, BID 3 F7, BR-BID-14): a petition RECEIVED or PROCESSING whose last day (`due_on`, in Vietnam) has passed is overdue; the first pass that finds it overdue sends one reminder (`bid.petition.overdue.v1`, remembered in `overdue_notified_at`) and writes the audit row `petition.overdue`. The job never answers a petition and never moves its deadline. Gauge `bid_petition_overdue` (alert `BID_PETITION_OVERDUE`); the pass is idempotent | API process only |
| `permit-expiry` | hourly tick, works in the 06:00 hour of Vietnam time only | the daily pass over the issued permits of each tenant (ST-PMT-006, PMT 3.1 step 5, BR-PMT-06): a permit with an end that is 60, 30, 15 or 0 calendar days from its last day (in Vietnam) gets one reminder for the level it has reached (`pmt.permit.expiring.v1`, turned into an in-app notification for the person in charge by the notification core, remembered in `alert_level_sent` so a second pass the same day sends nothing and a missed day sends the level of today); the day after its last day it becomes EXPIRED once (`pmt.permit.expired.v1`, which the issue intake of ISS answers with one issue) and the readiness of its dossier is counted again. It never renews or extends a permit: a renewal is a new permit that replaces the old one. Gauge `pmt_permit_expiring{days}`; the pass is idempotent | API process only |
| `gate-waiver-expiry` | hourly tick, works in the 00:00 hour of Vietnam time only | the nightly pass over the waivers of the permit gates of each tenant (ST-PMT-005, PMT 3.2 step 4): a waiver in force whose last day has passed becomes EXPIRED once, with the audit row `pmt.gate_waiver_expired` and the event `pmt.gate_waiver.expired.v1`. The gate did not wait for the job: the evaluation reads the last day, so a lapsed waiver lets nothing through even before the job has run; the job stores what is already true. Gauge `pmt_waiver_active` (the waivers in force after the pass); the pass is idempotent | API process only |
| `issue-sla` | every 15 minutes | the pass over the issues of each tenant that are being worked (ST-ISS-004, ISS 3.2, BR-ISS-03, BR-ISS-04): writes the day an issue became overdue (the deadline it missed, once, with `SLA_BREACHED` in its timeline) and raises the escalations whose threshold the working time of the SLA has reached: level 2 to the owner unit at `escalate_l2_pct` percent of the resolution time (100 by default) and level 3 to the task force that answers for the project at `escalate_l3_pct` (150 by default), one per level while open or accepted, announced by `iss.issue.escalated.v1` (in-app notification to the leaders of the project or the task force through the workflow of the tenant). It never closes the original issue, looks at OPEN, ASSIGNED, IN_PROGRESS, ESCALATED and REOPENED issues, at most 500 per tenant and pass (oldest deadline first), skips an issue a command is acting on, and leaves a level whose calendar year is not published or that has no task force to a later pass (counted in the result, never guessed). Counters `iss_sla_breach_total{level}`, gauges `iss_open_total{severity}` and `iss_escalation_pending`; the pass is idempotent | API process only |
| `integration-inbox` | every minute | takes up the inbound provider events that are due (`RECEIVED`, or `FAILED` whose wait of 1, 5 and then 30 minutes is over) for the providers that have a registered adapter, one row at a time with `for update skip locked`; a tenth failure parks the event as `DEAD` and raises `INTEGRATION_INBOX_DEAD` (ST-ADM-018; `docs/runbooks/integration-connectors.md`; the pass is idempotent) | API process only |
| `notification-dispatch` | every 5 seconds | sends the notifications that are due on each channel (ST-NOT-002): per channel, as its own bulkhead, it checks again that the recipient may still receive the message, takes each send up in a transaction of its own (`Queued` to `Sending`), calls the channel adapter with no transaction open and records the answer; a retryable failure queues the next send on the schedule of 30 seconds, 2, 10 and 30 minutes, a channel is done after five sends and the next channel of the plan takes over. A channel without a usable adapter has its sends suppressed (`ADAPTER_MISSING`, `MOCK_IN_PRODUCTION`). Sets `notification_dlq_gauge` and `notification_unknown_oldest_seconds` and raises `CHANNEL_CIRCUIT_OPEN`. Runbook: `docs/runbooks/notification-delivery.md`; the pass is idempotent | API process only |
| `notification-reconcile` | every 5 minutes | turns a send that was taken up and never reported back into `Unknown`, and asks the provider about each `Unknown` send of the last 24 hours by its idempotency key: a message the provider holds moves forward and closes its reconciliation task, one it never saw becomes a failed send that the schedule repeats, an adapter that cannot tell leaves it (BR-NOT-04; the pass is idempotent) | API process only |
| `subscription-cycle` | hourly | the pass over the subscription of each tenant (ST-SAS-008, BR-SAS-08): a trial whose end has passed becomes Active; a plan change set for the next cycle takes effect when its day has come (the subscription moves to the plan, the entitlements of the plan are recorded as a new version and the change is marked applied); a billing period that has passed gives way to the next, counted from the billing anchor; a subscription set to end ends with its period. It runs through the control role acting as the tenant (the plan catalogue is a control-plane table). The pass is idempotent | API process only |
| `allocation-extension-lapse` | hourly | lets the requests to carry capital over to the next year (ST-CAP-007, BR-CAP-04) that nobody decided lapse once their last day (`extended_to`, a Vietnam calendar day) has passed: they become LAPSED and can no longer be approved. It moves no money; the capital that an approved extension already carried over and that is left after its last day lapses with the closing of the year (ST-CAP-008, BR-CAP-04). It runs for each tenant through the tenant role. The pass is idempotent | API process only |
| `fiscal-year-relock` | every 15 minutes | locks again the fiscal years whose reopening (ST-CAP-008, `reopened_until`) has ended: the year goes from OPEN back to LOCKED, locked by the worker membership, and the capital that came back during the window and was not carried over lapses again as LAPSE entries of a new closing, with the ledger compared with the balances. A year that is locked is not touched; the pass is idempotent. It runs for each tenant through the tenant role | API process only |
| `entitlement-override-expiry` | every minute | the pass over the entitlement overrides of each tenant (ST-SAS-009, BR-SAS-10): an override in force whose window has ended becomes Expired and the tenant gets one new entitlement version (cause EXPIRY, `sas.entitlement.changed.v1`), so the exception stops counting within the minute the entitlement cache lives; a request that waited for a decision past the end of its window becomes Expired without a new version. The entitlement gate also ignores an override outside its window whether or not the pass has run. It runs through the control role acting as the tenant. The pass is idempotent | API process only |
| `land-stage-late` | hourly | the pass over the stages of land clearance of each tenant (ST-LND-010, LND 3.4): a stage that is not done and whose planned end is behind the Vietnam date of the pass (the planned day itself is not late) becomes LATE once, with the audit row `lnd.stage_late` and the event `lnd.stage.late.v1`, which the issue intake of ISS (ST-ISS-005) answers by opening one issue for the stage (BR-ISS-07: not a second while that one is open) and the stage remembers it in `blocker_issue_id`. A report that arrives after the day is judged by the same rule when it comes. The pass is idempotent | API process only |
| `access-cache-expiry` | every minute | drops the lapsed entries of the access cache of the process | API process only |

"Every tenant" is the tenant registry plus the platform tenant, which holds the audit rows of control-plane commands.
One tenant failing does not stop the others; the job then fails with `TenantJobsFailed` after the last tenant.

## One owner per job

A runner takes `pg_try_advisory_lock(hashtextextended('job:<name>', 0))` on a dedicated connection and holds it for the
run. Any number of API processes and command lines can run the same job; the one that does not get the lock records
`SKIPPED` and does nothing. The lock belongs to the database session, so a runner that dies (process killed, connection
cut, backend terminated) frees it, and the next runner of the next interval takes over. A run whose connection dies
before it ends is recorded `FAILED` with error class `JobLockLost`: another runner may have started the job meanwhile,
so check the job is idempotent for that window (all of the above are).

## Run a job by hand

```
DATABASE_URL_APP=postgres://...machvon_app...  DATABASE_URL_CONTROL=postgres://...machvon_control...  npm run jobs:run -- audit-seal
```

`audit-seal`, `audit-verify` and `idempotency-purge` are available. Exit code 0: the job succeeded, or another runner
holds it (the output says `SKIPPED`); 1: it failed (one JSON line per alert is printed before); 2: usage or
configuration. The relay and the access cache are refused with the usage line.

## Alerts

| Alert | Raised by | Context | First action |
|---|---|---|---|
| `JOB_FAILED` | the runner, once per failed run | `job`, `errorClass` (never a message) | read the process log for the job name at that time; the next interval runs again on its own |
| `AUDIT_CHAIN_BROKEN` | `audit-verify`, per tenant | `tenantId`, seal id, `fromSeq`, `toSeq`, `reason` | follow `docs/runbooks/audit-tamper-drill.md`; the `audit-verify` run also fails, so `JOB_FAILED` follows it |

A `JOB_FAILED` for `audit-verify` with error class `AuditChainBroken` is the same incident as the `AUDIT_CHAIN_BROKEN`
alert before it, not a second one.

`job_runs_total{job, outcome}` counts the runs (`SUCCESS`, `FAILED`, `SKIPPED`). A job whose counter stops moving is not
running anywhere: check the API processes and the scheduler of the deployment.

## In the API process

`npm start` (`apps/api/src/serve.ts` through `bootstrap.ts`) starts the workers once the server listens, unless
`WORKERS_ENABLED=false` (see `docs/runbooks/api-runtime.md`). The code is `apps/api/src/workers/`:

- `startWorkers` builds the job runner (one owner per job, advisory lock on a connection of the relay role), the outbox relay and
  `standardJobs`, and registers `runner.scheduled(name, JOB_INTERVAL_SECONDS[name])` for each job on the `IntervalScheduler`
  (`@machvon/kernel`) with the intervals of the table above. The next run is timed from the end of the previous one, so a slow
  job never overlaps itself. The first run of a job comes one interval after the process started (the daily job therefore
  runs only in a process that lives for a day, or in the one that took over from it).
- `createOutboxConsumers` and `createOutboxPublisher` are the `publish` of the relay: every delivery goes to the tenant provisioning
  consumer (`sas.tenant.requested.v1`), the entitlement cache consumer (`sas.entitlement.changed.v1`), the tenant status consumer
  (`sas.tenant.status_changed.v1`) and the notification consumer (only for event types registered and Active in
  `notification_event_type`). A delivery fails when any consumer fails; the relay retries it and the inbox row of each consumer makes
  the ones that succeeded a duplicate. The end-to-end stack (`apps/api/test/e2e-stack/serve.stack.ts`) runs this same code with a 1
  second relay interval.
- One alert sink (`createAlertSink`: one JSON line on standard error per alert, and the webhook `ALERT_WEBHOOK_URL` when set) is
  handed to the relay, the seal job, the job runner and the signed-context check of every consumer, so `OUTBOX_LAG`,
  `OUTBOX_EVENT_DEAD`, `OUTBOX_CONTEXT_TAMPERED`, `AUDIT_CHAIN_BROKEN` and `JOB_FAILED` leave the process.
- A tick never takes the process down. The runner records a failed run (`FAILED`) and raises `JOB_FAILED`; a failure that still
  escapes the runner is written as one line `{"level":"error","message":"worker tick failed","job":...,"errorClass":...}` (class
  only, never a message) and raised as `JOB_FAILED` as well. The schedule carries on with the next interval.
- Shutdown: on SIGTERM the HTTP server stops accepting, the timers are cleared at once and `stop()` waits for the tick in flight
  before the pools are closed. A second `stop()` is a no-op.

Several API processes can run the workers together: each job has one owner at a time, the others record `SKIPPED`. A process that
only serves requests runs with `WORKERS_ENABLED=false`. With the switch off nothing of the above is created: no timer, no pool
connection of the relay role, and the outbox events wait (`OUTBOX_LAG` fires from a process that runs the relay).

Limits that remain (TODOS.md, "Workers in the API process"): the provisioning saga runs on the MOCK infrastructure ports and the MOCK
mailer until the real adapters of Task 20 exist; a provisioning run that was in flight when its process died is not resumed after the
restart (`resumeUnfinishedRuns` is not called: it needs a single owner, which the Temporal adapter provides); the `job_runs_total`
counter has no exporter in the process yet (the history of the runner is in memory).

Tests: `apps/api/test/workers/workers-runtime.test.ts` (database lane: an event written by an HTTP command is relayed with no manual
run, a planted tamper is found by the started verify job and alerts, stop and the switch), `workers.test.ts` and
`outbox-consumers.test.ts` (no database: failing ticks, intervals, tampered deliveries).
