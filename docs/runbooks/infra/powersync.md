# Runbook: PowerSync

Story: ST-KERNEL-002, ST-KERNEL-045. Declaration: `infra/components/powersync.json`; alert rules `infra/alerts/powersync.json`.

PowerSync replicates the sync roles' view of PostgreSQL to mobile clients through a logical replication slot. It reads
through the `machvon_sync` role, which sees only what the sync rules allow.

## Entering use

The component stays `PLANNED` until `npm run infra:check -- --require-entered powersync` passes: this runbook, the
alert rules and a restore test (rebuild the service from the sync rules on a restored database and sync one client).
See [README](README.md).

## Sync lag

Alert `powersync-sync-lag`: sync lag is above 60 s for a bucket.

1. Check the logical slot on the primary (`pg_replication_slots`): an inactive slot retains WAL and fills the disk,
   see the disk section of the PostgreSQL runbook.
2. Check the service health and the sync role connection count.
3. If the slot cannot be recovered, recreate it; clients resynchronise from the server. Offline writes already queued on
   devices are not lost: they replay through the command pipeline with their idempotency keys.

## Sync rules of the weekly report (ST-DIS-017)

The reference rules are `infra/powersync/sync-rules.reference.yaml`, **generated** from `packages/contracts/src/dis-sync.ts` (`npm run contracts:mobile-pack`; a test fails when the file is out of date). PowerSync reads the write-ahead log, which does
not pass row-level security, so the tenant and the scope of the member are in the queries and nowhere else. Status: PROPOSED REFERENCE. The queries use joins and subqueries that the PowerSync dialect does not take, so the file cannot be published as it is; the spike of ST-KERNEL-002 (not run) translates them (the list is in the file) and `mobile-sync.test.ts` is the acceptance of the translation.

1. Deploy: not before the spike. Build the deployable rules from the reference (projections and bucket parameters in place of joins), publish them after the publication and the `machvon_sync` grants exist, and run the proof on the real service. Do not edit the generated reference by hand.
2. Revoking a person: the grant command ends the rows of `sync_membership_scope` of that membership (`effective_until`). The parameter query no longer returns them, so the buckets are empty at the next sync and the phone removes the rows.
   To check by hand: set the token of the person, run the parameter query of `dis_reports`, expect no row.
3. Rebuild after a restore: re-create the service from the file on the restored database, sync one test client of each tenant, and compare the rows with `apps/api/test/dis/mobile-sync.test.ts` (the same queries run on PostgreSQL). Record the result here; the component stays `PLANNED` until that evidence exists.
4. A rule that is changed is changed in the source, the generated files are committed together, and the contract pack for the mobile group (`docs/dis-mobile-contract.md`) is regenerated by the same command.
