# UAT evidence: the number that says whether the product is accepted

Two generated documents answer two different questions and neither may be edited by hand.

| Document | Generated by | Question | Source of truth |
| --- | --- | --- | --- |
| `docs/UAT-COVERAGE.md` | `npm run uat:trace` | Does every acceptance criterion of a finished story have a live test? | the titles of the tests in the repository |
| `docs/UAT-EVIDENCE.md` | `npm run uat:evidence` | Which screens and requirements of the design have been **run** and passed, with evidence? | the run store `docs/uat-run-results.json` |

`npm run uat:evidence:check` (in `npm run lint`) keeps the second document current. `npm run uat:gate` is the completeness gate for a release:
it fails while any screen or requirement is not complete. It is not part of `npm run lint`, because a repository that is still being built
is honestly red; the release checklist asks for it.

## What counts

A row of the document (a screen, a requirement) is the worst state of the tests the design names for it (`traceability.json`, defined in
`test_cases.json`):

| State | Meaning | Complete? |
| --- | --- | --- |
| `PASS` | every test has a recorded PASS **with its evidence** | yes |
| `WAIVED` | every test that is not PASS has a valid waiver | yes |
| `UNPROVEN` | a PASS that lacks part of its evidence: claimed, not shown | no |
| `NOT_RUN` | the run store does not name the test, or says so | no |
| `SKIPPED` | the test was skipped | no |
| `FAIL` | a test failed, or the record says something that is not a result | no |
| `GAP` | the design names no test that exists for the screen or the requirement | no |

NOT_RUN, SKIPPED and FAIL never count as PASS, and a waiver never counts as a pass in the critical section.

## The run store

`docs/uat-run-results.json` is written by the run that produced the evidence (the pipeline of the release), not by a person:

```json
{
  "runId": "release-2026-11-01-r1",
  "build": "commit sha of the build that was tested",
  "schemaVersion": "last migration applied",
  "datasetSha256": "hash of the fixture dataset",
  "results": {
    "UAT-AC411": {
      "result": "PASS",
      "at": "2026-11-01T02:14:00Z",
      "build": "commit sha",
      "schema_version": "1365",
      "dataset_sha256": "64 hex digits",
      "request_ids": ["01J9..."],
      "evidence": "docs/evidence/release-2026-11-01-r1/UAT-AC411.json"
    }
  },
  "waivers": [
    { "target": "UAT-AC77", "owner": "Product owner", "reason": "Why it cannot run", "approved_by": "Head of QA", "expires": "2026-12-31" }
  ]
}
```

A PASS carries **when it ran, the build, the schema version, the hash of the dataset, the ids of the requests that were made and a link to the
evidence** (redacted screenshots, the requests and responses with secrets removed). Missing any of them, it is UNPROVEN.

A waiver names a test, a screen or a requirement, an owner, a reason, the person who approved it and a day. It excuses a result until that day
included; after it, or without any of its fields, it fails the gate on its own.

## Critical tests

`docs/uat-critical.json` lists, by area (money, isolation, restore), the requirement prefixes whose tests are critical. The product owner
changes it. The report shows how many critical tests have a PASS; a release is not complete below 100 percent, whatever is waived elsewhere.
