# MOB: the mobile security review (ST-MOB-041)

Scope: `apps/mobile` at the state of the repository on 2026-11-03, against OWASP MASVS 2.x (STORAGE, CRYPTO, AUTH, NETWORK, PLATFORM, CODE, RESILIENCE, PRIVACY) and the three acceptance criteria of ST-MOB-041: AC-ST-MOB-041-1 / UAT-NFR-TENANCY-07 (a copied container of a rooted device reveals nothing), AC-ST-MOB-041-2 / UAT-AC500 (a hostile proxy and a modified request write nothing under another tenant), AC-ST-MOB-041-3 / UAT-AC501 (a revoked membership is purged at the first online contact). Requirements: NFR-TENANCY-07, NFR-SECURITY-03, NFR-PRIVACY-02.

Method: reading of the sources, the manifests and the project files; host tests written for each rule that can be asserted without a phone (`test/hardening/`, listed at the end); no device, no emulator and no proxy was available, so every claim about the behaviour of a platform is marked **device**. The first pass wrote only new files and listed the changes to existing code under "Fix list"; a second pass (2026-11-03) made those changes, finding by finding, and turned each pin test into a test of the fixed behaviour. The Android and iOS sides were written but **not built** (no build runs on this machine): that they compile and do what they say is a **device** claim.

## Threat model

| actor | capability | what they want |
|---|---|---|
| lost or stolen phone, locked | the file system of the phone after a restart, no PIN | tenant data, tokens |
| lost or stolen phone, unlocked, or a person who left the organisation | the application as installed, a rooted device, a copy of the container, a backup | tenant data of a tenant they no longer belong to |
| hostile Wi-Fi or proxy | sees and changes traffic; may have had a CA installed on the phone (by the owner, by malware, or by an MDM that inspects TLS) | tokens, the content of commands, a command moved to another tenant or replayed |
| a person with a modified phone | root or jailbreak, a hooking framework, a debugger | bypass the biometric prompt, read memory, alter the application |
| another application on the phone | the custom URL scheme, the shared storage, the clipboard | the authorization code of the sign-in, files |
| a hostile or confused tenant user | the API with a valid token | another tenant's rows through sync |

Out of scope here (server, covered in `apps/api/test`): the rules of `POST /sync/batches` (device registration, tenant from the token, receipts, key conflict), the PowerSync bucket rules (`packages/contracts/test/sync-rules-check.test.ts`), the identity provider.

## Decisions

### D-SEC-01 Root and jailbreak: a policy of the tenant, never a block

A detector on the phone is bypassed by the person who controls the phone (a hooking framework returns "not rooted"), and a hard block locks out the field engineer whose only phone is rooted by an old custom ROM while stopping no attacker. So the signal is a **risk input**: `lib/core/security/device_integrity.dart` turns the signals (`rooted`, `jailbroken`, `debuggerAttached`, `hookingFramework`, `emulator`) behind the port `DeviceIntegritySource` into a decision by the tenant mode:

| mode (set by the server per tenant) | modified phone | effect |
|---|---|---|
| `off` | proceed | nothing |
| `warn` (default, and what an unknown value means) | warn | the person is told once per session; the reason code is counted in the telemetry |
| `restrict_sensitive` | restrict | as `warn`, and approvals, signing and the biometric unlock need the server's agreement first (step-up) |

There is no mode that stops the application: drafts and sign-out stay reachable. A detector that fails or does not answer in 2 s is "unknown" and changes nothing. A debugger counts only in a release build; an emulator is named and changes nothing. Reason codes (`DEVICE_ROOTED`, `DEVICE_JAILBROKEN`, `DEBUGGER_ATTACHED`, `HOOKING_FRAMEWORK`, `EMULATOR`, `INTEGRITY_UNKNOWN`) have the shape of the `reason_code` of the telemetry, and nothing else about the phone is reported. **Wired** (`INTEG-01`, fixed): the platform port is a method channel `vn.machvon/device_integrity` (`MethodChannelIntegritySource`; the Kotlin of `MainActivity.kt` and the Swift of `AppDelegate.swift` answer it with a few conventional checks: `su` binaries and test keys, a loaded Frida or Xposed library, a debugger, an emulator; on iOS the usual jailbreak files and dylibs, `P_TRACED`, the simulator). The signals are read once per session after sign-in by `integrityMonitorProvider` (`lib/features/release/integrity_monitor.dart`, started by `SessionServices`), the decision is kept in `integrityProvider`, the first one of a session is counted as `device.integrity` events with one `reason_code` each, and the person is told once by a banner of the shell that they can close. **The mode comes from the version-policy answer** (`integrity_mode`, read by `VersionPolicy.tryParse`); the field is not in `openapi.json` (the version policy is a contract the story asked of SAS and is not there yet) and the answer is read before anyone signs in, so it is a mode for the deployment, not yet for the tenant: **absent or unknown it is `warn`**. Under `restrict_sensitive`: the approval and the return of a task (MOB-25, MOB-26) and the signing (MOB-67) ask for the second factor first (`IntegrityStepUp`, which makes the session ask for MOB-03 exactly as a 403 `MFA_REQUIRED` does, and which the server still judges), and the biometric unlock can neither be turned on nor release the stored credential (`AuthService.unlock` returns false without the prompt, the person signs in again). The adapters were not verified on a rooted and a jailbroken phone (**device**, T6).

### D-SEC-02 Certificate pinning: off for the pilot, with the conditions to turn it on

Pinning defends against one attacker: a proxy whose CA the phone trusts. Against it, without pinning, the application is readable and alterable (tokens are short-lived, 5 minutes for the tenant token, and the server judges every command by its token, so such a proxy can read what the user can read and send what the user can send, but cannot move a command to another tenant). Against it the cost of pinning here is high: the three `HttpClient` sites of the application (API transport, chunk transport, document fetcher) must all be covered; the API base URL is one host per build and the certificate is renewed automatically, so a leaf pin would break every installed phone within a quarter and an intermediate pin needs a backup pin and a rotation drill; tenants whose organisation inspects TLS on its own network (a corporate proxy with its CA) would be locked out of the application; and a mistake cannot be fixed by an update when the phones that need the update cannot reach the update's address.

Decision for the pilot (R4): **pinning is off** (`kPinningPolicy` in `lib/core/security/pinning_policy.dart`, tested), the compensating controls are the short tokens, PKCE, the idempotency keys, the server-side tenant envelope, and the monitoring of the hostile-proxy case in the device matrix (see below). The policy is built so that it can be turned on without redesign: a pin is the SHA-256 of the SubjectPublicKeyInfo; a pinning policy refuses to exist with fewer than two valid pins (a backup); the three modes are `off`, `reportOnly` (a mismatch is let through and counted) and `enforce`; the server can relax the mode but never tighten it (`loweredBy`), so a bad rotation can be rescued without an update.

The policy is wired as far as the decision allows (`pinningPolicyProvider`): it is `kPinningPolicy` lowered by the `pinning_mode` of the version policy, so the server can relax and never tighten it, and for the pilot it is `off` whatever the server says. The three HTTP sites do not consult it yet, because a pin check on `dart:io` needs a trust configuration those sites do not have; that is the third condition below.

Conditions to raise it (record the date and the signer here when done): a rotation drill run once with the backup pin; the remote relaxation reachable from the version-policy answer; the three HTTP sites covered by one factory; `reportOnly` observed for one release with a mismatch rate near zero; the list of tenants that inspect TLS known and a per-tenant setting agreed. The first step is `reportOnly`, never `enforce`.

**device**: whether `dart:io` on Android trusts user-installed CAs is to be verified on a phone with a proxy CA installed (the Android network security configuration does not apply to `dart:io`, and the application declares none). The review assumes it does.

### D-SEC-03 Screen capture and the app switcher: protect the screens that show money and decisions

The thumbnail of the app switcher and a screen recording can reveal amounts, approvals and documents. Decision: Android sets `FLAG_SECURE` and iOS covers the window when the scene resigns active, **on the screens of approvals, signing, payments and the weekly report amounts**, switched by a method channel the screen calls; not on the whole application, because a block everywhere also stops the screenshots a person legitimately needs, which is a product-owner trade-off to confirm. Implemented (`SEC-04`, fixed): `kSecureScreenIds` in `route_policy.dart` lists MOB-14 to 17, 20, 21, 23 to 27, 56, 60 and 67; the router wraps them in `SecureScreen`, which holds the protection while the screen is the one shown (not when it is covered or on a tab that is not shown) through `SecureWindowController` (a count, so overlapping screens do not switch it off early) and the channel `vn.machvon/secure_window` (`set`, `enabled`). `MainActivity.kt` sets and clears `FLAG_SECURE`; `SceneDelegate.swift` covers every window of the scenes with a plain view when a scene is about to become inactive or the screen is captured, only while the protection is on. A page pushed by hand over a protected screen (the PDF viewer, the comparison and the enlarged page of a signing) covers it, and a covered screen releases its protection, so every such route is built with `secureRoute` (`secure_screen.dart`), which wraps it in `SecureScreen`; a hardening test fails on any other page route in `lib`.

### D-SEC-04 The local store

Kept as built (ST-MOB-005): one SQLite3 Multiple Ciphers file for each user of each tenant, a 256-bit key from `Random.secure`, the key only in the Keychain or Keystore (`first_unlock_this_device`: usable by a background send after the first unlock, never restored to another phone), file and key named by a digest, purge deletes the file, the journals, the uploads folder and the key. The tests of `test/hardening/local_store_security_test.dart` read the file and its log, find none of a bearer-token string, a free-text marker, a tenant id, a user id, a table name or the SQLite header, show that a copied container does not open with another key, with a short key or as plain SQLite (and does with the right key, so the search could have found something), that a copy made before a purge is useless after it, and that no store holds a row of another tenant or user. What the file cannot protect: a key extracted from the Keystore of a rooted phone by someone who can run code as the application (**device**). The plain files of `SEC-03` are now short-lived: the copy of a photograph that the picker leaves in the cache is deleted once the photograph is prepared, refused or given up; the prepared copy of an upload is deleted when the server says `CLEAN`; the prepared photographs of a draft and the original kept beside them are deleted when the command that carries the draft is accepted; and on iOS the folder `offline` of Application Support is flagged `isExcludedFromBackup` at launch, so the photographs of a draft that is not sent yet are not in a backup either. Android keeps its backup off.

### D-SEC-05 Sync abuse

The phone sends no tenant and no user in a batch (the body is `device_id` and the items; no header names a tenant): the tenant is the one of the bearer token, which the server judges (`apps/api/test/sync`). On the phone a row of another tenant or user that got into the store is never sent, a session of another tenant blocks the flush, and an answer for a key that was not in the batch creates and moves nothing (`test/hardening/sync_abuse_test.dart`). What a hostile proxy with a trusted CA can still do is what D-SEC-02 accepts: read and alter the commands of the person whose phone it is, and drop or forge an answer (a forged "accepted" would make the phone forget a command the server never received; the answer is not signed).
