# MOB: documents awaiting signature on the phone (ST-MOB-023)

MOB-67 lets a leader open the final PDF of an outgoing document, compare it with the version before it and sign it, away from the desk. Numbering and the seal of the organisation stay with the clerk on the web (DOC-06), and the leader's signature stays valid after numbering because it was added to the file as an incremental update (DOC.md BR-DOC-14). The code is in `apps/mobile/lib/features/document_signing`; the server half is the DOC module (`startLeaderSigning`, `completeSigningSession`, `getOutgoingDocument`, `getDocumentVersionDownload`), and the web counterpart is DOC-05 and DOC-22, whose sentences the screen reuses.

## The screen (`/approval/mob-67`)

Without a parameter it lists the documents waiting for the leader (`listOutgoingDocuments?status=SUBMITTED`, at most four pages of 50, with a note when there are more), those that name the person as signer first. With `?doc=<id>` it opens one document (`getOutgoingDocument`):

| part | shows |
|---|---|
| Văn bản | title, type, the named signer, the status, and that numbering and the seal are the clerk's |
| Tệp PDF và các phiên bản | the current file (version, stage, pages, start of its hash), **Xem PDF**, **So sánh với bản n** |
| Ký | the certificate in force, the way of signing, and the two steps below |
| Kết quả ký | once the server says the leader signed: when, the verdict of the server's verification, the signed version, and whether the content is unchanged |

## Reading the PDF

`PdfLoader` asks the server for a short-lived signed address (`getDocumentVersionDownload`, needs a clean scan; 409 `SCAN_PENDING` and a blocked file are said in words), fetches the bytes into memory and **trusts nothing until it has checked them**: the address must be https (or a path on the API; `mock://`, `file:` and a protocol-relative address are refused), no redirect is followed and no bearer token is sent (the address is the authority), the body is cut at 50 MiB, the first bytes must be `%PDF-`, and the SHA-256 must be the one the server declared for the version (and for the download). The bytes are never written to the phone: they live in memory for the screen and the document is closed when the screen leaves.

**Package: `pdfx` 2.11** (`pubspec.yaml`; it brings `photo_view`, `synchronized`, `extension` and `universal_platform`). It draws a page with the renderer of the system (PdfRenderer on Android, PDFKit on iOS), so the app carries no PDF engine and nothing is downloaded at build time; the alternatives either bring their own native engine and a download at build time (`pdfrx`) or are commercial (`syncfusion_flutter_pdfviewer`), and `flutter_pdfview` shows a native view that a test cannot look at. The package is used in one file, `pdfx_engine.dart`; everything else speaks to the port `PdfEngine`/`PdfDoc` (open bytes, count pages, draw page n at width w as a PNG), so the screens, the comparison and the tests run on the host with a renderer that returns images. The adapter itself is tried against a fake of the platform interface of pdfx (`documents_test.dart`): it draws on a white ground, one page at a time (the system renderer cannot draw two at once), and closes pages and documents. A page tap opens it large (pinch and move).

## Comparing with the previous version

The previous version is the newest one before the current in the order of the versions. **So sánh** opens both files and says: the two versions (stage, pages, time, start of the hash; "the same hash: the files are identical" when they are), and **page by page** whether they differ. A page both versions have is drawn at the same small width and compared pixel by pixel (a channel may differ by 24 of 255 and 0.2 percent of the pixels may differ before the page counts as changed, so anti-aliasing is not a change); a page only one has is "new in this version" or "only in the previous version". The result says where to look: opening a page of either version is a tap, and reading stays the leader's act. It is a visual comparison, not a comparison of text.

## Signing: two commands and a port

1. **Start** (`startLeaderSigning`, under the version of the document the screen showed): the certificate in force that ends last and the adapter of the port. The server fixes the digest and answers 202; the document stays `SUBMITTED`.
2. **Complete** (`completeSigningSession`, under the version of the session): the proof of the signer. The server embeds the signature, verifies it at once and the document becomes `LEADER_SIGNED` with a new version built on the final PDF.

The proof comes from `SigningPort` (provider `signingPortProvider`): today `RemoteCaOtpPort`, the remote certificate authority confirmed with the one-time code on the signer's own device, exactly as the web DOC-22 (CXN-DOC-07); the vendor SDK that signs the digest on the phone is ST-MOB-032 (below), which implements the same port (`needsTypedCode` false, `unlocksCredential` true, `prove` returns the CMS signature and the digest it signed). The session has 15 minutes; the phone shows the time the server gave and never judges it with its own clock: the server answers 409 `SIGNING_SESSION_EXPIRED`, the screen then offers a new session. The server does not change the stored status of a session that ran out (it expires it inside the next `startLeaderSigning`, which then opens the new one), so reading the document again still shows it open: the refusal itself is what the screen remembers (per session id) to stop offering that session for confirmation and to offer "Mở phiên ký mới" instead; a session the server already shows as `EXPIRED` is offered the same way.

**Biometric (AC-ST-MOB-023-4).** When the key is held on the phone the screen asks the system prompt first; a refusal stops everything and nothing is sent, a success only lets the key be used. The answer of the prompt is not a parameter of `prove` and appears in no request: a test reads the body sent (`{"cms_signature":…,"client_digest_hex":…}`) and finds nothing of it, and with the code port the prompt is never asked.

## The provider's SDK on the phone (ST-MOB-032)

The vendor SDK that signs on the phone (chosen under D05, SPIKE-CA-SANDBOX) is native code that cannot be built here. What the application needs from it is the three calls of `VendorSigningSdk` (`vendor_sdk.dart`): `availability`, `identity` (the certificate it holds) and `signDigest` (the SHA-256 digest the server locked, never the document). `MethodChannelVendorSigningSdk` speaks them over the channel `vn.machvon.app/vendor_signing`; its contract is written in the class and tried on the host against a mocked channel (arguments, answers, the codes `SDK_UNAVAILABLE`, `USER_CANCELLED`, `CERTIFICATE_NOT_ACTIVE`, `NO_CERTIFICATE`, an answer that lacks the signature, the digest or the signer). A build with no native module answers nothing, which is "not installed". The vendor's own text and codes never reach the screen or a log. `VendorSdkSigningPort` is the `SigningPort` on top (`LOCAL_AGENT`, no typed code, the application's biometric prompt only unlocks the credential); `--dart-define=MACHVON_SIGNING=vendor_sdk` selects it, anything else keeps the remote CA with the one-time code.

- **Ready before anything is created.** `SigningPort.readiness` is asked before `startLeaderSigning`: an SDK that cannot be used, a holder with no certificate in it, or a certificate that is not the one registered for the signer (the names are compared as distinguished names: same attributes, any order, any case of the type; and the SHA-256 fingerprint of the certificate in the SDK is compared with the registered `fingerprint_sha256`, because a renewed certificate keeps its name and the server compares the fingerprint of the signature; an SDK that does not report its fingerprint is judged by the name alone, and the server decides on the real one) open no session (AC-ST-MOB-032-3, UAT-AC427). The state is "retryable": nothing was started, the document still waits, "Try again" asks again.
- **Checked before it is sent.** The SDK must say it signed the digest the server locked and as the registered certificate (its name and its fingerprint); otherwise nothing is sent (the server would refuse it with `DIGEST_MISMATCH` or `SIGNATURE_INVALID`, and the signer should not find out after the fact). An SDK that is unavailable at the signature leaves the session open on the server (it lapses by itself) and nothing is completed; the retry completes once, under one key, with one signature. Closing the SDK's own confirmation (PIN or biometric) signs nothing and sends nothing. A signing interaction is guarded from the first tap to its end, not only while the request is on its way: the check of the SDK, the prompt of the phone and the SDK's signature each run once at a time, the confirm button, the code field and the retry buttons are off while one is on, and the guard is let go on every way out. A PDF whose opening finishes after the viewer was left is closed on arrival, so leaving the viewer never leaves a native handle behind.
- **Revoked or expired certificate (AC-ST-MOB-032-2, UAT-AC406).** The register is the server's: `startLeaderSigning` answers 422 `CERTIFICATE_NOT_ACTIVE`, no session exists afterwards, the SDK is never asked to sign and nothing is completed; the screen says so with the code and offers no retry (trying again does not change a certificate). The SDK can say the same at signing time (the vendor checked its status): same sentence, nothing sent.
- **The result (AC-ST-MOB-032-1, UAT-AC430).** After the signature the screen reads the document back: the verdict of the server's verification, and "the signer named on the signature is the holder of the certificate registered for you" when the name the server read off the signature is that certificate's subject; when it is not, a warning not to pass the document to the clerk. The valid signature itself is the server's verification (`verifyDocumentSignatures`), tried against the vendor sandbox by SPIKE-CA-SANDBOX.
- **MOB-25.** An approval carries no signature (`decideApprovalTask` has no field for one); MOB-25 says so and points to MOB-67, where the leader signs with the provider's SDK after the second-factor check (`MFA_REQUIRED` is handled by the session, as for the code).

## The rules

1. **Online only, never queued.** `SigningCommands` has no way to reach the offline queue. Offline, or on a copy kept on the device, the buttons are disabled and the screen says why; `syncStatusProvider` holds 0 commands and the server received no `POST` (UAT-AC426).
2. **The named signer.** The signature is offered to the person whose membership is the `signer_user_id` of the document (and in a session that is not read-only); everyone else reads the reason. The server judges again: 422 `SIGNER_NOT_AUTHORIZED` (UAT-AC414, with the threshold of the delegation of authority), 403 `SELF_APPROVAL_DENIED`, `CERTIFICATE_NOT_ACTIVE`, `SIGNING_SESSION_OPEN`, `DOCUMENT_STATE_INVALID`, `VERSION_CONFLICT`, a second factor (`MFA_REQUIRED`, handled by the session) and a licence each have their sentence and their stable code.
3. **A provider that is down (UAT-AC427).** 503 `PROVIDER_UNAVAILABLE` and `SIGNING_ADAPTER_UNAVAILABLE` are said as retryable: the document stays awaiting signature, **nothing says signed** (what the screen says about the signature is only what the server says, `leader_signed_at` and the verdict, never the outcome of a request), the document is read again after every refusal, and "try again" sends the same command under the same key.
4. **A lost answer is not a new signature.** "Result not known", and sending the same confirmation again reuses the key and the version, so the server records it once.
5. **AC-ST-MOB-023-1 (UAT-AC403).** After the signature the screen reads the document back: the leader signature `VALID`, the signed version, and **"the content is unchanged"** only when the signed version's `prefix_sha256` is the hash of the final PDF that was read (the signature is an incremental update, so the file it was built on is part of the version); otherwise a warning that says not to pass it to the clerk. The byte-level proof (revision 1, the prefix `[0, L0)` unchanged) is the server's test; the phone shows what the server recorded.

## What only a device can prove

With the vendor SDK (ST-MOB-032): the native wrappers themselves (Android and iOS) answering the channel; the SDK's own PIN or biometric confirmation, its secure element and its behaviour when the app is backgrounded in the middle; a certificate revoked or expired at the CA being refused by the SDK and by the server; the CMS signature produced on a phone verifying in the vendor's verification tool with the signer identity equal to the certificate (SPIKE-CA-SANDBOX); the SDK being killed, absent or out of licence; storage, permissions and logging of the SDK (TK-MOB-032-3, the security review). Before that: that `pdfx` draws a real PDF with a signature field and an incremental update on Android (PdfRenderer) and on iOS (PDFKit), its speed and memory on a long document, and the look of pages at 200 percent text; the system biometric prompt and a key behind it (with the SDK of ST-MOB-032); the one-time code arriving on the signer's device and the 15 minutes; a connection cut between the request and the answer; the real signed address of the object storage (its host and its redirect behaviour are not known: the object storage of the platform, KERNEL-024, is not bound and the mock gives `mock://` addresses, which the phone refuses); against the CA sandbox the cases of sign, refusal and provider down (SPIKE-CA-SANDBOX).

## Gaps

- No allowlist of hosts for the signed address: the storage provider is not chosen. The phone accepts any https host, sends no credential to it and checks the hash of what it receives.
- The comparison is visual. A comparison of the text of the two versions needs the text of the PDF, which the server does not give.
- MOB-67 has no "return to the drafter with a reason" (the web DOC-22 has one): the phone has no list of the rights of the person, and `doc.outgoing.review` is not the leader's by default. The return is on **DOC-22** (`docs/mob-qms-doc-screens.md`), which is this signing view with the return added; there the button is offered on every submitted document and the server judges the right.
- The list shows the documents in the scope of the reader that wait for a signature, not only those that name the person; the ones that do are first.
