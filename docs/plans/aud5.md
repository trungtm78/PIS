## Legal document type (MD.02, lane aud5)

Gap left by aud2: the legal-document catalogue `ENT_LEGAL_DOC_TYPE` was read by nothing on the document side, and `createProjectDocument` (a public-edition command) could not say which legal document a file is.

- **Seam.** `ProjectDocumentExtension` (`packages/db/src/project-document-extension.ts`, injection token `PROJECT_DOCUMENT_EXTENSION` in `apps/api/src/modules/doc/tokens.ts`). The repository commands `createProjectDocument` and `updateProjectDocument` ask it about the optional member `legal_doc_type` before anything is written and hand it the document afterwards, in the same transaction. The public edition binds nothing, so the commands use `PublicProjectDocumentExtension`: no member or `null` is what the request always was, a named type is refused 422 `VALIDATION_FAILED` on `legal_doc_type` (reason `NOT_AVAILABLE`). The enterprise edition binds `EnterpriseProjectDocumentExtension` through the enterprise API module `IPF` (`apps/api/src/editions/enterprise/index.ts`); public code imports nothing of it (`npm run edition:check`).
- **Judgement.** A code is accepted when the catalogue holds it on the business day: the built-in types and the codes a tenant added through an approved rule that is in force; an unknown or expired code is 422 on `legal_doc_type` (reason `UNKNOWN_TYPE`, or `FORMAT` for something that is not a code). `null` clears the type.
- **Storage.** Enterprise-owned side table `project_document_legal_type` (migration V2940, block `AUD5-1` 2940-2959, RLS forced like its neighbours), one row per document, with who set it and when. The public table `project_document` is not touched. Contract: the optional member `legal_doc_type` joins `ProjectDocumentCreate` and `ProjectDocumentUpdate` only; the document views stay as they were (the type is read through the investment profile).
- **Change of the type.** Decision by governance: a wrong type must be correctable, and the type is part of what a document says it is, so `updateProjectDocument` accepts it with the same judgement and the same optimistic version (a change that names the type alone still moves the version of the document, by writing the note back as it stands). The trail keeps the row `doc.repo.document_created` / `document_updated` as they were and adds one row `doc.repo.document_legal_type_set` with `legal_doc_type: { from, to }` only when the type moved; the public edition never writes it.
- **Profile.** `getProjectInvestmentProfile` gains `legal_documents`: one group per type with at least one ACTIVE document of the project that the caller may read, `{ legal_doc_type, label, issuer, purpose, count, documents: [{ id, title, reference, effective_from, effective_to, effective_state, status }] }`; the groups follow the order of the pack, then the codes a tenant added by code, then a type that left the catalogue (shown under its code, `issuer` and `purpose` null); documents newest first, at most 20 per group (`count` is the whole number). Documents are listed in the scope of `doc.repo.read` (`listProjectDocuments`), not of the project read: who may read the project but not its documents sees an empty list. Pure shaping `legalDocumentsOf` in `investment-profile.ts`, read in `investment-profile-store.ts`.
- **Not built.** A select for the type on the DOC-24 create form: the form has no read of the catalogue open to an ordinary document author (the governance reads need the governance permission), so it needs a small enterprise read operation first; the API accepts the member today.
- **Tests.** Edition package: `legal-doc-type.test.ts` (pure judgement, the extension on a recording transaction, the public extension), `investment-profile.test.ts` (grouping, order, cap, archived, type left the catalogue). API with the real database: `apps/api/test/editions/project-document-legal-type.enterprise.test.ts` (one database, two applications: the public one proves the commands are unchanged and refuse a named type, the enterprise one stores, validates, changes, clears, audits and feeds the profile; scope of the documents).

## BI sign-off on the board (BC.02, fork aud5-bi)

Gap left by aud3: BI-02 and its presentation did not show the prepared, checked and approved block because the board is not tied to a dashboard.

- **Model (deepest governance).** The sign-off belongs to the published version of a dashboard: the facts exist only there (author of the version, check of the publication request, publisher). The current version is not used, because a later save makes a draft the current one while the published version stays the one that was approved. BI-02 is therefore read as a published dashboard by choice; without a choice it is the unsigned board of all certified metrics and says so in words. No API change: `getDashboard` already returns `versions[]`, each with its `sign_off`, and the list gives the status.
- **Built.** Choice of dashboard on BI-02 (dashboards with status PUBLISHED, `?dashboard=`, link from BI-01), tiles = certified metrics of the published version, `SignOffBlock` on the page and a compact strip on every page of the presentation (the dialog is titled with the dashboard), a version that pins its dataset versions (`PINNED`) is read at the pinned snapshots only (`snapshotsOf`; found by the independent review, round 1), honest states (none published, no certified metric left, unreadable dashboard, list not readable = no choice offered). Strings in the part `aud5-bi`.
- **Other presentations.** HOME-09 (command center), BAN-01 and DIR period have a presentation mode but show the figures of the command center, the committee and the directives, which are no dashboard version; BI-03 has no presentation mode (its preview already carries the block). Nothing else in BI lacked the block.
- **Not touched.** The BI dataset registry and views (lane int2).
- **Tests.** `apps/web/src/screens/bi/BoardSignOff.test.tsx` (15: model, snapshot pinning, board without and with a dashboard, address, presentation strip, incomplete, unbound presentation, empty states, error and retry, library link); the existing BI-02, BI-01, BI-03 and PresentationMode tests stay green.

## Investment profile screen IPF-01 (MD.01, MD.02, CN.01, parent)

Gap left by aud2: the profile existed as an API only.

- **Screen.** `IPF-01`, module `IPF` (the module the API already mounts for the profile), kind detail, added to `screen_catalog.json` through `contract-patch` (spec `docs/plans/aud5-ipf.contract.json`) and to the area Dau tu of `navigation_architecture.json` after PRJ; `npm run routes:generate` and `node scripts/help-index.mjs generate` rebuilt the route table and the on-screen guide. `IPF` joins `ENTERPRISE_ONLY_MODULES`, so a public process mounts none of the module and the public web build opens no route of it; the screen loader sits in the enterprise bundle only (`apps/web/src/editions/enterprise/screen-loaders.ts`), code in `apps/web/src/editions/enterprise/screens/ipf` (`ProfileScreen.tsx`, `sections.tsx`, `model.ts`, `hooks.ts`, `ipf.css`).
- **What it shows.** Project and plan year (address `?project=&plan_year=`, or the choice form from the projects the caller reads), type of the project, new start or carry-over flag with the start year and what it rests on, the annual plans the split is read from, the findings (`MILESTONE_ORDER`, `REQUIRED_SKIPPED`) named by the label of the milestone, the milestones of the catalogue in order with state, days and the evidence each asks for against the legal documents the project holds (a milestone reached with no document of its kinds is said so), the legal documents by type with issuer, purpose, count, state and a link to DOC-25, and the plan split by origin: Nghi quyet PVN (`GROUP_ASSIGNED`) against Quyet dinh cua Tong cong ty (`BOARD_APPROVED`) and the rest, with the documents behind each. Honest states: no project chosen, project not found (404, the same word whether it exists or not), refusal, failure with retry, no plan line, no classified document, flag not known.
- **Decisions.** Read only; no write path. The type of a decision document is shown by the label of the cap screen and falls back to the code. The evidence of a milestone is counted from the legal documents the API sends, so a type that left the catalogue is counted under its code. A year typed into the form is judged before it is sent (four digits, 2000 to 2100); one in the address that is not a year is ignored and the server answers for the current year.
- **Design pack and UAT.** Module spec `05_modules/IPF.md`, story `ST-IPF-001` (epic `EP-IPF`), backlog `BL-IPF-01`, design cases `UI-IPF-01` and the cases `UAT-ENT-IPF-01..06`, `UAT-ENT-SEC-17` and `UAT-ENT-BI-01` in `test_cases.json`, `traceability.json` and `docs/uat/ent/uat.json` (the ledger and the index follow). Five of them name the integration tests of the profile and of the legal document seam (`investment-profile.enterprise.test.ts`, `project-document-legal-type.enterprise.test.ts`), `SEC-17` is a row of the permission matrix; the browser walks (`IPF-06`, `BI-01`) stay manual with their reason.
- **Tests.** `ProfileScreen.test.tsx` (25: model and screen, 100 percent of statements and 96 percent of branches); the edition, route, help and every-route tests were updated for the ninth enterprise screen (`edition.test.tsx`, `screens.enterprise.test.ts`, `generate.test.ts`, `registry.test.tsx`, kernel `edition.test.ts`).
