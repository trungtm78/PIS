## Decisions (owner rule 2026-11-08: deepest governance, extensibility, no scope cut)
1. **Audit detail is a side record, the sealed row commits to it.** `audit_event` keeps the 17 columns that the seal and the export format fix. The full before/after goes to a new append-only `audit_event_detail` (one row per audit row, RLS forced, no update or delete for the runtime role). The sealed `safe_diff` of the row gets a `detail_ref` object (`sha256`, `bytes`, `redacted_paths`), so the Merkle leaf commits to the detail and any later change of the detail is detectable. No change to the seal, the export format or `verifyAuditExport`.
2. **Opt-in per business object class, default OFF.** `audit_detail_policy` (tenant, `resource_type`, `enabled`, `max_bytes` per row, extra sensitive keys, reason, version) is changed by a command that needs `adm.audit_detail.manage` over the whole tenant, a reason, and is itself audited. A call site passes `detail: { before, after }` on its audit entry; `AuditWriter` stores it only when the policy for that `resource_type` is enabled (one indexed read, only for entries that carry a detail). Call sites wired in this lane: period reopen (DIS), HPM push (ENT-2). The period figure revision (ENT-3a) and any later business object only add `detail` to their audit entry.
3. **Redaction is a pure kernel rule** (`audit-detail.ts`): the existing key regex (`password`, `secret`, `token`, ...) plus the policy keys plus value shapes (a bearer token, a 13-19 digit card-like number, an e-mail local part is NOT redacted: it is business data); personal fields of the class `PERSONAL` are replaced by a keyed marker. Over the byte cap, the detail is truncated by dropping the largest leaves first and marks `truncated: true` with the number of dropped paths (the row is never refused: an audit write must not fail a command).
4. **Log caps never delete business evidence.** `log_capacity_policy` (per record class: `max_rows`, `max_bytes`, `warn_pct`) covers the TECHNICAL classes of `retention.ts` plus `audit_event` and `audit_event_detail` as **monitor-only** classes (alert, never purge: BR-ADM-11 and the sealed trail). For a technical class over its cap the nightly run archives the oldest rows beyond the cap into a hashed JSONL file (`log_archive_batch`, purpose `log_archive`, stored through the shared file pipeline) and only then deletes exactly the archived rows, **never a row younger than the platform minimum period** and never a row under a legal hold. If nothing is eligible, the class stays over its cap and the alert `LOG_CAPACITY_EXCEEDED` says so. `LOG_CAPACITY_NEAR` fires at `warn_pct` (default 80). A cap must be at least the rows that the platform minimum period keeps (validated against the last reading), so a cap cannot be a back door to shorten retention.
5. **FX rates are an MDM catalogue, not a new store.** Type `FX_RATE` (rule-like: `legal_basis` and approval by publication, maker is not publisher through the MDM framework). One entry per pair and kind (`USD_VND_OFFICIAL`), one effective-dated version per day or period (`period_kind` DAY | MONTH | QUARTER | YEAR). Attributes: `base_currency`, `quote_currency` (must exist in CURRENCY), `rate` (exact decimal string), `rate_kind` (OFFICIAL_AVERAGE, BUY, SELL, TRANSFER, CLOSING), `period_kind`, `source` (SBV, VCB, PVN_GROUP, OTHER), `source_ref`, `approval_ref` (the decision or minutes that fixed it). The conversion helper is pure in the kernel (`fx-rate.ts`): pick the rate in force on a day, convert with exact decimals and the scale and rounding of the target currency, cross through VND, inverse, never a float; golden tests. **Public behaviour stays VND-only**: nothing in the public flows calls the helper; amounts keep `*_vnd` columns.
6. **Equipment procurement is a read model, not a new copy of the data (R21).** Enterprise module `EQP` (screens EQP-01 list, EQP-02 detail) over a small register `equipment_procurement_item` (the line of the investment plan that is bought as equipment: project, owning unit, name, planned value, optional link to the BID package and the CTR contract). Selection result comes from `procurement_result`, contract value from the latest effective `contract_revision`, disbursement from `payment_request` (PAID), the e-GP state from `procurement_external_link` and the connector health. Scope: `bid.read` over the project subtree (the unit of the project owns the line); contract and payment figures are shown only when the caller also holds `ctr.read` and `pay.read` in scope, else masked (`null` plus a `masked` list). A "how to get data" block shows the state of the e-GP file import (NEVER_IMPORTED / FRESH / STALE, layout `WORKING-ASSUMPTION`, acceptance PENDING_EXTERNAL) with the steps to download and hand over the files; no connection is opened.
7. **Delay-cause catalogue = MDM-17 `ISSUE_CATEGORY` with two attributes** (`delay_cause` boolean, `cause_group` choice). The kernel `delayCauseOptions` builds the grouped list; the web hook `useDelayCauses` and the select `DelayCauseSelect` are shared by the project issue form (ISS-02, causes first) and by the narrative forms of ENT-3b (read-only contract: key of the entry, never a label). ENT-3b files are not edited; its plan did not exist at the time of writing (D:\PIS-ent3b has no `docs/plans/ent3b.md`), so the hook is documented here.
8. Screens: ADM next free ids (settings of audit detail and of log caps in one ADM screen pair), EQP-01, EQP-02; FX rates use the generic MDM catalogue screens (typeForms + catalogues entry), no new screen.
