# Plan of lane VND-3 (contractor investigation and contractor portal)

Branch `lane/vnd3`, worktree `D:\PIS-vnd3`, migration block 2440-2459. Items of `research-vendor.md`: V6 (related-party graph and bid-rigging screening, auditors only), V14 (continuous screening against the national debarment list), V15 (contractor portal, annual re-confirmation), V16 (petition and claim statistics), V17 (remediation plan), V18 (OCDS parties export). Built on VND-1 (registry, accounts, certificates, debarment case, reputation ledger) and GOV-10 (red flags). VND-2 builds the controls (independence, finance, load, bid security, subcontracts, risk grade, performance evaluation) in parallel: nothing of that is built here; the portal answers requests of any kind through a generic request/response channel that VND-2 feeds.

## Decisions (owner rule: deepest governance, best extensibility, no scope cut)
- Investigation is a separate path from red flags: a **lead** (`vendor_investigation_lead`) is a ranked signal about contractors (a link cluster, rotating winners, cover bids, price pattern, same file metadata, shared submission origin, affiliate of a restricted contractor). Never a conclusion, never shown to the people who took part in the packages it is about (`vendor_lead_involved`, 404 as for red flags), never shown to a contractor (database policy denies the portal path). Review in the manner of G4-3: take, propose dismissal (reason), a different auditor confirms; or confirm the signal as right (measures the false alarm rate, KPI 9); or refer to an investigation.
- The link graph is a **computed projection** (`contractor_party_link`) from the keys VND-1 already keeps (tax head, address, telephone, e-mail, representative, owner name/identity key, account blind index) plus the submission trace (IP/device key, file metadata keys) that this lane lets the receiving officer record per proposal (`proposal_submission_trace`). Edges carry kind, strength and the evidence key shown only as a short fingerprint. Graph view: an accessible SVG radial layout written here (no graph library in the web package), with a table fallback.
- Screening reads the list the **existing file-import path** already keeps (`egp_record` kind RESTRICTION); international/PEP lists enter through `screening_list_entry` (a bulk command with source code, as-of day and reference). Matching is deterministic: tax code (head) decisive, name similarity supporting, a name alone is never a hit above "possible". A hit above the hold score puts the contractor on a **screening hold** (new gate check `SCREENING` in `VendorGate`, refusal 422 `CONTRACTOR_SCREENING_HOLD`) until another person confirms (opens the debarment case from the record through the VND-1 hook) or dismisses it. Runs nightly (job), on a profile change, after an import and on request.
- Portal: a contractor is a `GUEST_CONTRACTOR` membership with `contractor_id` (ADM-17). Portal operations take the contractor from the caller, never from the path or body. At database level the portal path sets `app.portal_contractor_id` and **restrictive policies** limit every contractor-scoped table to that contractor and deny every investigation, screening and red flag table (negative tests prove a contractor reads no other contractor and no red flag). Permissions `vnd.portal.*` are added to the system role GUEST_CONTRACTOR (migration updates existing tenants).
- Generic request channel `contractor_portal_request` (kind, subject, due clock counted by the working-time engine, response, review). Annual re-confirmation (`contractor_reconfirmation`, rule `VENDOR_RECONFIRMATION`) and integrity declaration (`contractor_integrity_declaration`, versioned text from the rule) with an overdue alert and an automatic stop of "good standing" flag shown to staff, never a block.
- Legal numbers are rules flagged UNVERIFIED with source and as-of: `VENDOR_LINK_RULE`, `VENDOR_BID_RIGGING`, `VENDOR_SCREENING`, `VENDOR_PORTAL`, `VENDOR_RECONFIRMATION`, `VENDOR_REMEDIATION`, `VENDOR_OCDS_EXPORT`, registered by `registerVendor3Rules` in `governance-rules.ts`.

## Portal access hook (BE-2)
- A contractor reaches the portal only as a `GUEST_CONTRACTOR` membership bound to its contractor (`membership.contractor_id`, ADM-17). Guests are invited through contracts (BR-IAM-08: the validity of a guest is bounded by the latest planned completion of the contracts of its grants, and the grants are scoped to contracts), so a contractor with no contract has no way to obtain portal access yet. Follow-up for IAM: allow a guest grant scoped to the contractor itself (or an invitation without a contract for annual re-confirmation); until then `createVendorPortalRequest` answers 422 `CONTRACTOR_PORTAL_NOT_BOUND` for a contractor with no active guest account, and the staff list of re-confirmations still shows it.
- The five portal rights (`vnd.portal.read`, `.respond`, `.certificate`, `.reconfirm`, `.remediation`) are added to the system role GUEST_CONTRACTOR by migration V2447 (existing tenants) and must be added to `SYSTEM_ROLES` in `packages/db/src/system-roles.ts` for tenants provisioned later (not done in this lane: IAM file).
