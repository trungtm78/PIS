## Decisions (owner rule 2026-11-08: deepest governance, extensibility, no scope cut)
1. **The PUSH step holds, it does not complete.** A new table `approval_step_hold` (one open hold per task) and two engine moves: `ApprovalStore.decide` takes an optional `hold` hook that runs after every authorisation check and before the task is written; when it answers HELD the task stays Pending, the instance stays Running and only the hold row is written. `ApprovalStore.release` finishes the decision as the person who was held, without asking the authorisation again (it was judged when the push was made), so the final command of the business type runs only when the receiver confirmed. States of a hold: `AWAITING_RECEIPT`, `PUSH_FAILED` (retry with the same key), `PUSHED` (receipt accepted, decision finished), `REJECTED` (receipt rejected, the report goes back by the usual return), `CANCELLED` (instance cancelled or returned). The SLA sweep skips a held task (the push alerts `HPM_PUSH_FAILED` and `HPM_PUSH_STALE` speak for it).
2. **The seam is a port.** `ApprovalPushPort` (public API, `modules/adm`, no word of the enterprise edition) is provided by the HPM module of the enterprise edition (`HpmApprovalPush`, same folder as the controllers); when no module provides it the PUSH step is the person step it has always been, so every existing DIS test runs unchanged. The port builds the push through `HpmPushStore.send`: key = organisation | layout | period | rN (R8) where N is the revision of the report, `issuedHeadRevision` = the newest revision of the report (R17: a push of an older revision is refused `REPORT_OUT_OF_DATE`, the hold is not created). The receipt recorded on HPM-01 (`recordHpmReceipt`) releases the hold in the same transaction.
3. **One staged flow for three owners.** The kernel registry `STAGED_APPROVALS` names, per owner, the business type, the rule code (`REPORT_ACCEPT`, `FND_FIGURE_ACCEPT`, `IND_ENTRY_ACCEPT` of the rule type `APPROVAL_WORKFLOW_DEFINITION`), the resource type and the package builder; `ReportApprovalFlow` keeps its public shape and becomes a thin subclass of the generic `StagedApprovalFlow`. FND batches reuse `submitFundingFigures`, `acceptFundingFigures` and `returnFundingFigures` (staged tenants start an instance at the hand-in, the acceptance becomes the decision of the task of the person who decides; final command `fnd.figures.accept`). IND gets a real batch (`ind_entry_batch`, DRAFT/SUBMITTED/ACCEPTED/RETURNED) because entries were written at once: `submitIndicatorEntryBatch` judges the figures and keeps the rule warnings, `decideIndicatorEntryBatch` approves or returns; a tenant without the staged rule keeps `enterIndicatorFigures` as it is. The two new business types are not enabled by default; `MACHVON_APPROVAL_BUSINESS_TYPES` enables them and the boot guard then needs the real handlers the FND and IND bindings register (R14).
4. **Return with warnings (BBH 43).** A return of a FND or IND batch carries the warnings that were kept at the hand-in (non-blocking rule violations) plus the reason, to both the person who entered and the approver (audit row + event + the batch read); the approver sees the same list at the decision.
5. **Adjust in the next period (TH.01).** `hpm_adjustment` (state PROPOSED, APPROVED, REJECTED, APPLIED) and `hpm_adjustment_entry` (append-only journal of every move with actor and time): a wrong figure in an accepted period is not overwritten; a signed amount is booked for the next period of the same layout, proposed by one person, decided by another (CHECK proposer <> decider), applied once by the push of the next period (the package carries the applied entries). Rules are pure in the edition package (`hpm-adjust-rules.ts`): the target period must be the next one of the same grain, the source revision must be accepted, a reason of 10 characters, one open adjustment per (layout, period, subject).
6. **Contract by `scripts/contract-patch.mjs` only**: new operations `submitIndicatorEntryBatch`, `decideIndicatorEntryBatch`, `listIndicatorEntryBatches`, `proposeHpmAdjustment`, `decideHpmAdjustment`, `listHpmAdjustments`; additive fields (`hold`) on the workflow instance read of DIS; error codes registered.
