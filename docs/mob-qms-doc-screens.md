# MOB: the four screens of the navigation that are not MOB screens (QMS-09, QMS-10, DOC-22, DOC-23)

The mobile navigation lists 72 screens: the 68 `MOB-nn` screens and four screens of two modules whose catalogue row says `platform: mobile` (`screen_catalog.json`): **QMS-09** the site diary on the phone, offline; **QMS-10** a site photograph with the checks of its EXIF and its place; **DOC-22** a leader approves and signs a document; **DOC-23** the incoming letters to handle. Until now they showed the not-implemented screen and nothing linked to them (finding NAV-02 of `docs/mobile-security-review.md`, now fixed). The behaviour is `QMS.md` 3.1 and 3.4 and `DOC.md` 4 (`Design/MACHVON_Design/01_Documents/05_modules`); the operations are the ones of the web; the web screens that share them are `apps/web/src/screens/qms/offline` (QMS-09), `qms/capture` (QMS-10), `doc/mobile` (DOC-22 and DOC-23).

All four are registered features (`lib/features/<name>/<name>_feature.dart`, `dart run tool/generate_registry.dart`), with Vietnamese and English strings of their own (`mob.dryhub.*`, `mob.sitepic.*`, `mob.docapv.*`, `mob.docin.*`), the standard states through `DataView` and `StateBoundary`, no right of the person kept on the phone (what a person may do is what the server says for the record; the server judges every command again), and labels for TalkBack and VoiceOver. None of them is read-only on the phone: the catalogue marks none so.

| screen | feature | opened from | route |
|---|---|---|---|
| QMS-09 | `diary_hub` | the app bar of MOB-61 (contracts) | `/projects/qms-09`, `?diary=<id>` for the settling of one diary |
| QMS-10 | `site_photo` | the app bar of MOB-61 | `/projects/qms-10`, `?contract=<id>&diary=<id>` |
| DOC-22 | `doc_approval` | the app bar of MOB-23 (approvals) | `/approval/doc-22`, `?doc=<id>` for one document |
| DOC-23 | `doc_incoming` | the app bar of MOB-23 | `/approval/doc-23`, `?doc=<id>` for one letter |

## DOC-23: the incoming letters to handle (`doc_incoming`)

The letters assigned to the person that wait for handling. The server filters on one status at a time, so the screen reads `ASSIGNED` and `PROCESSING` (up to 4 pages of 50 each, and says when there are more) and keeps the letters that are the person's: the letter names them as handler, or the server offers them an action (`actions.startProcessing`, `actions.resolve`). The late ones come first (the most days late), then by deadline, a letter with no deadline last. A row shows the number (`10 · 10/REG-DEN-2026`) or "no number yet", the subject, the sender, the leader's directive (the bút phê) or "no directive yet", the deadline, the status, the urgency and, when the server says so, "Quá hạn n ngày (hạn dd/mm/yyyy)"; the days late are the server's (`overdue_days`), the clock of the phone judges nothing. A letter opens with `?doc=<id>`: the letter, the history of assignments, the file by the start of its hash, the resolution when there is one, and the two commands.

* **Start handling** (`startIncomingDocumentProcessing`) and **resolve** (`resolveIncomingDocument`, 5 to 2000 characters, counted in characters) are one request each, under the version of the letter on the screen (`If-Match`) and an `Idempotency-Key` that belongs to the person's intention: "result unknown" after a lost answer sends the same command again with the same key and version, a final refusal ends the intention (a new request after the cause is gone is a new command with a new key), the letter is read again after every refusal. An overdue letter can still be resolved; the screen says the lateness is recorded (UAT-AC420).
* **Nothing is kept on the device** (the catalogue rule: "dữ liệu cá nhân và tệp mật không đồng bộ offline"). The reads of the screen use `DataView(keepCopy: false)`: no copy is written, and a lost connection is the offline state, not an old list; the letter's file is not read on the phone at all. Offline, in a read-only organisation, on a letter that no longer waits or that the server offers nothing on, the buttons are not drawn or are off, with the reason beside them; nothing is queued.
* **"Mở tệp"** has no operation behind it: a letter's file (`file_object_key`) is not served by any endpoint of the API (`getDocumentVersionDownload` is for the versions of outgoing documents), and the web DOC-23 only links to DOC-13, which does not show the file either. The screen shows the fingerprint of the file and says the file is opened on the web. This is a gap of the server (below).

Refusals have the sentences of the web (`NOT_ASSIGNEE`, `DOCUMENT_STATE_INVALID`, `RESPONSE_DOCUMENT_NOT_ISSUED`, `VERSION_CONFLICT`, `MFA_REQUIRED`, `LICENSE_EXPIRED`, a denial, a validation, an ended session) with the stable code under them.

## DOC-22: approve and sign a document (`doc_approval`)

The signing view of MOB-67 (`document_signing`): the documents that wait for the leader (those that name the person as signer first), the final PDF, the comparison with the version before it, the way of signing and the confirmation with the one-time code of the remote certificate authority (CXN-DOC-07), plus what the web DOC-22 has and MOB-67 left out: **return the document to its drafter with a reason** (`returnOutgoingDocument`, the reason is 10 to 2000 characters, as the server takes it).

* **One implementation of the signing, two screens.** `SigningWaitingList` and `SigningDocumentView` (`document_signing/screens/signing_screen.dart`) take the screen they open and the words of their title, and a footer; MOB-67 passes nothing, DOC-22 passes the return card. Every rule of MOB-67 holds for DOC-22 (AC-ST-DOC-020-1, UAT-AC426): signing is online only and never queued, `SigningCommands` has no way to reach the offline queue, a session that lapsed after 15 minutes is refused by the server with 409 `SIGNING_SESSION_EXPIRED`, the document is read again and a new session is offered. DOC-22 is a **secure screen** and carries the **integrity restriction of signing** exactly as MOB-67 does (`kSecureScreenIds`, `kIntegrityRestrictedScreens` in `core/navigation/route_policy.dart`: the one change to `lib/core`).
* **The return** is one request under the version of the document, with a key; a retry after a lost answer reuses both; offline, from a copy, or in a read-only organisation it is off with the reason beside it; a document that no longer waits (returned, signed) is no longer offered. **Decision:** the phone has no list of the rights of the person and `doc.outgoing.review` is not the leader's by default (`docs/mob-document-signing.md`), so the button is offered on every submitted document the person can open and the server judges the right: a 403 is said in words with its code and the reason stays in the form.
* "Hình thức ký" is the line of the adapter on the sign card ("Dịch vụ ký từ xa của CA, xác nhận bằng mã dùng một lần"). The signature by the provider's SDK on the phone (`MACHVON_SIGNING=vendor_sdk`, ST-MOB-032) works in DOC-22 the same way, because the port is the one of MOB-67.

## QMS-09: the site diary on the phone, offline (`diary_hub`)

The diary itself is written, saved and signed in MOB-62 (`site_diary`), which already queues a save as the command `site_diary.append` under the key the phone made (UAT-AC358) and settles a queued diary in conflict in MOB-42 (UAT-AC366). QMS-09 is the screen that shows where every diary stands and settles what MOB-62 cannot. Two tabs:

* **Trên máy** (on the phone): the drafts of the encrypted store read together with the commands of the queue. Each row has the day, the contract, the start of what was written, and its state: *xung đột đồng bộ* (opens MOB-42 to choose, nothing is overwritten silently), *máy chủ từ chối* (with its code), *chưa xác định kết quả*, *đang gửi*, *chờ gửi*, *bản nháp trên máy*, *đã gửi*; the ones that need the person come first. A row opens the diary on its contract and day in MOB-62. A count says how many diaries are not sent and that **changing the organisation is blocked until they are sent or dropped** (the account screens read the same queue through `pendingWorkProvider`). The screen sends nothing by itself. A draft with nothing written is not a diary yet and is not listed.
* **Trên máy chủ** (on the server, `DataView`, a copy is shown with its `as_of` when the server cannot be reached): the diaries with copies that devices left and nobody settled (`has_conflict=true`) and the drafts that wait for the contractor's signature (`status=DRAFT`, `actions.contractorSign`, no copy waiting). A draft to sign opens MOB-62, where the signature is made (OTP, online only). A diary with copies opens the settling (`?diary=<id>`).

**The settling** (`resolveDiaryConflict`, AC-ST-QMS-002-1, UAT-AC62): the diary of the day and each copy are shown side by side (work, workforce, notes); the person picks the copy (when there are several), the way (keep the diary of the day, or take the copy over a *draft*; a signed diary can only be kept) and writes the reason (required, 2000 characters); one request under the version of the diary, with a key; offline, from a copy, in a read-only organisation, with no copy waiting or without the right the server offers (`actions.resolveConflict`) it is off with the reason beside it. Nothing is sent before the person chooses. **Not on the phone:** joining the two contents into new content (`MERGED`); the screen says so and points to the web (QMS-03).

## QMS-10: a site photograph (`site_photo`)

The person takes or chooses photographs (the tools of `field_evidence`: the camera after the rationale of MOB-06, the gallery as the way round, the pipeline that checks the type, compresses and handles the metadata), links them to a **contract** (the contracts of MOB-61, with the same copy) and, if they wish, a **diary** of it, writes a **caption** (2000 characters), and sees the **flags** before anything is kept: how many photographs have no place, how many have no time of capture, how many are the same file as one already registered for the contract or as another photograph of the same capture (the SHA-256 of the prepared file against `get_resources_site_photo`; when that cannot be read the screen says repeats were not checked and goes on). A flag is a note for review and never stops a photograph; the flags of time, zone, repetition and EXIF are the server's, given when a photograph is registered.

* **The place is kept only with the consent** (BR-QMS-06, UAT-AC367, AC-ST-QMS-003-2): the position is read after the person agreed, the rationale of MOB-06 was shown and the phone allowed it, while the application is in use; without the consent the place and the time are removed from the photograph the moment it is prepared and no coordinate is written to the store or to the file that goes up; taking the consent back takes the place and the time out of the photographs already prepared, at once. A stored place without the consent is not trusted when read back (`FieldPlace.fromJson`).
* **Saving works with no connection.** The capture (contract, diary, caption, the place with its consent, the photographs) is kept in the encrypted store under one operation id, and each photograph is handed once to the uploader (`ownerKind` `site_photo`, `ownerRef` the operation id): it goes up in chunks when there is a network, is scanned, and waits as a clean upload (MOB-19 opens for that capture). The list "Ảnh đã chụp trên máy" shows each capture with how many photographs are up and a way to drop it (uploads that have not finished are cancelled, files and record removed). Leaving the form removes the prepared files of a form that was never kept; the files of a capture that is kept (or is being kept) stay with it, also after a save that ended badly, so the retry and the uploader still find them (`SitePhotoService.discardUnkept`).
* **The registration in the photo register is not made from the phone** (`registerSitePhoto`): it takes the `object_key` of a file of the file service of kind `site_photo`, and no operation gives the phone one (the upload endpoints of the phone make keys of kind `sync_attachment`, which `registerSitePhoto` refuses with 422 `VALIDATION_FAILED`; there is no upload endpoint for the `site_photo` purpose). The web screen QMS-10 asks the person to type the key and says the phone fills it in; it does not. The capture is therefore kept with everything the registration needs, and the screen says the registration cannot be done from the phone yet. This is the same gap as `docs/mob-field-issues.md` and `docs/mob-site-diary.md` name for photographs.

## Gaps and decisions (for the lead)

1. **QMS-10 cannot register** (above). Closing it needs a server operation that either takes the id of a clean `sync_attachment` in `registerSitePhoto` (as `commentIssue` takes a document version), or hands the phone a `site_photo` upload. When it exists, the registration is a command built from the `PhotoRecord` the screen already keeps (`client_operation_id` is the operation id, `geo_consent` and the position only with the consent).
2. **DOC-23 "Mở tệp"**: no endpoint serves the file of an incoming letter. A `getIncomingDocumentDownload` like `getDocumentVersionDownload` would let the phone read it with the viewer of MOB-67 (and the rule "tệp mật không đồng bộ offline" would hold: the viewer keeps the bytes in memory only).
3. **DOC-22 return** is offered to everyone who can open the document; the server decides (see above).
4. **QMS-09 server tab** lists at most 2 pages of 50 diaries of each list and says when there are more.
5. **QMS-10 needs the contract list once**: the contracts come from the read of MOB-61 (shared copy); a phone that never opened it and has no network shows the offline state, not an empty form.
6. `lib/core` was touched once, backwards compatibly: `route_policy.dart` lists DOC-22 beside MOB-67. Entry points are icon buttons in the app bars of MOB-61 and MOB-23 (no body layout changed).

## What only a device can prove
