# The simulation of an allocation (ST-CAP-013)

Module document: `Design/MACHVON_Design/01_Documents/05_modules/CAP.md` (F8, CAP-09, UAT-AC233, UAT-PLAN-65). Migration `V1371__cap1_allocation_scenario.sql`. Operations: `createAllocationScenario` (`POST /allocation-scenarios`, `capital.scenario.run`), `runAllocationScenario` (`POST /allocation-scenarios/{id}/run`, `capital.scenario.run`, `If-Match`), `promoteAllocationScenario` (`POST /allocation-scenarios/{id}/promote`, `capital.reallocation.propose`, `If-Match`), and one read added to the contract, `listAllocationScenarios` (`GET /allocation-scenarios`, `capital.read`). The pure rules are `packages/kernel/src/cap-scenario.ts`, the store `packages/db/src/cap-scenario-store.ts`.

## The rule

A scenario asks a question of a plan and never changes the plan: it states **assumptions** (moves of capital) and **constraints** (limits), is **run** to a result, and may then be **promoted** to a DRAFT reallocation proposal. Creating, running, promoting and reading write the scenario (and the proposal, when promoted) and nothing else: no ledger entry, no allocation line, no balance, no plan, no reservation (UAT-AC233 counts them before and after).

- **The assumptions** are `{ "moves": [...] }`, one to 200 moves, each `from_allocation_line_id` (a line of the base plan), `to_project_id`, `amount_vnd` (a whole positive number of dong) and an optional `rationale`. The same line and project twice, a key the contract does not know, or an amount that is not whole dong is 422 `VALIDATION_FAILED` naming the field.
- **The constraints** are any of `min_remaining_vnd` (a donor line keeps at least this much in all, and never less than what is reserved, committed and disbursed on it; may be 0), `max_move_vnd` (no single move is larger) and `max_total_vnd` (the moves together are not larger).
- **The base plan** is a plan in force (PUBLISHED) — a plan still being drawn up is seen only by those who draw it up and approve it, so it is 409 `PLAN_NOT_PUBLISHED` when the scenario is created, and again when a scenario is run after its plan stopped being in force — of the year asked (422 `VALIDATION_FAILED` `plan_year` otherwise); the caller needs the permission over the unit of the plan (403 `SCOPE_DENIED`); a plan of another tenant is 404. The input snapshot is optional when creating; it must exist (422 `input_snapshot_id`).
- **The run** applies the moves to a copy of the lines. The recipient of a move is the line of the receiving project in the same appropriation, bucket, source year and budget level, as a proposal resolves it. A line that gives and receives ends with the difference. A donor line must end with at least what is reserved, committed and disbursed on it (the balance of the line) and at least `min_remaining_vnd`; a line that only receives is not judged. The result keeps `ran_at`, the total moved, the moves with their lines, each line before and after with the minimum it keeps, and each project before and after, with everything the plan gives the project (the lines the moves do not name count).
- **Infeasible** is 422 `SCENARIO_CONSTRAINT_INFEASIBLE` with `violations` (`BELOW_MINIMUM`, `MOVE_ABOVE_LIMIT`, `TOTAL_ABOVE_LIMIT`, `NO_RECIPIENT_LINE`, each with its figures) and nothing kept: the scenario stays as it was. A move to a project that holds no line on the same appropriation is `NO_RECIPIENT_LINE` here (a proposal says `TRANSFER_UNBALANCED` for the same case).
- **The states** are `DRAFT` (no result) → `RUN` (a result; it can be run again, the result replaces the old one) → `PROMOTED` (final). `ARCHIVED` is in the table for retention and no command enters it. A version that moved is 409 `VERSION_CONFLICT`; a step the state does not allow is 409 `STAGE_TRANSITION_DENIED`.
- **Promotion** needs a result: a scenario that was never run is 409 `SCENARIO_NOT_RUN`. It needs a frozen input snapshot (none: 422 `VALIDATION_FAILED` `input_snapshot_id`; not frozen: 422 `SNAPSHOT_NOT_FROZEN`). What was true when it was run is judged again at promotion, against the plan and the balances as they are then: a scenario the plan has made infeasible is 422 `SCENARIO_CONSTRAINT_INFEASIBLE` and nothing is promoted. The proposal is a DRAFT drawn by the one who promotes, on the base plan and the snapshot, with the moves as its lines; its code is `SCN-` and the code of the scenario (shortened with a hash when it would not fit in 50 characters) and a code that is taken is 409 `DUPLICATE_KEY`. It then follows the submission, decision and application of ST-CAP-010.
- **The trail.** The audit rows `capital.scenario_created|run|promoted` (and `capital.reallocation_drafted` for the proposal) carry the ids, the statuses and the year; the words of the rationale are not repeated.
- **The database.** What the scenario asks never changes (code, year, snapshot, plan, constraints, assumptions, who made it); it starts as a DRAFT with no result; the status moves along DRAFT → RUN → RUN → PROMOTED only; a result exists exactly when it was run and the proposal exactly when it was promoted; the result that was promoted does not change; nothing is deleted.

## The read

`listAllocationScenarios` lists the scenarios on plans of the units in the scope of the reader, newest first (`status`, `plan_year`, `limit`, `cursor`). Each carries `actions` (`run`, `promote`) for the caller over the unit of its plan.

## The screen (CAP-09)

`ScenarioScreen`: a form to create a scenario (code, a published plan, an optional frozen snapshot, the three limits, and moves that take from a line of the plan and give to a project), the list with the code, the plan, the number of moves, the total moved and the status, and the buttons that `actions` and the permissions allow (run, run again, promote). The result shows each project before and after with what it gains or loses, under a note that nothing was written to the plan; an infeasible run lists the limits it broke in words. A reader and the read-only mode see the list only.

## What is not done

- The method of the simulation is not given by the document; it is the one above (moves as assumptions, floors and limits as constraints). Other kinds of assumption (growth of a disbursement rate, a new appropriation) are not part of it.
- `ARCHIVED` has no command; the retention of two years after archiving belongs to the retention jobs.
- The result names projects by id; the screen reads their codes from the register of projects and falls back to the start of the id for a reader who may not read it.
