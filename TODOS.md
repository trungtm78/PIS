## M2f lane B design gaps (change request entries needed)
- `acceptInvitation` is declared `x-plane: tenant` with permission `invitation.accept`, but the person who accepts holds an identity token and no tenant token yet (the invitation is what gives them a membership). It is implemented like `selectTenantContext`: an identity command (`@Public` plus the invitee guard), idempotent and audited by its own pipeline. Change the contract to say so (no tenant plane, no permission).
- IAM.md 3.3 answers an already used token with 409 `INVITATION_EXPIRED` (there is no used-invitation code); a token that names no invitation, a wrong secret and a token of another tenant are all the same 404 `RESOURCE_NOT_FOUND`, so the answer never says whether an invitation exists.
- The seat limit comes from the latest valid `license_revision`: `seats` for staff, `quota_json.guest_seats` for guest contractors (IAM.md 3.3 names `guest_seats` but SAS never defines the key). A tenant with no revision has no limit. Define the key in the licence claims.
- `MemberInvite` has no `reason`, so the audit row of `inviteMember` has none; without `initial_grants` the person receives the MEMBER role on their unit (what `session.self` needs), which no document states.
- The invitation message goes through the `InvitationMailer` port; the only adapter is the in-memory MOCK one until the OMNI email channel exists (R1), so no invitation mail leaves the system yet. The events `iam.membership.invited|activated|suspended|ended.v1` are not in the notification catalogue.
- The hourly job that expires pending invitations (IAM.md section 9) is not implemented here; an expired invitation is expired on its next acceptance attempt. It belongs to the scheduler of Task 12.
- The last-owner guard (BR-IAM-07) runs before the rank rule on purpose: no one outranks a TENANT_OWNER (rank 99), so after the rank rule it could never be reached.
- `EffectiveAccess` (openapi, `getMyEffectiveAccess`) has `additionalProperties: false` and free-form `grants` and `delegations_in` items, and no `mode` or permission list at the top: the API puts role, scope (units with breadcrumb, projects, contracts), permissions, window and `state` (ACTIVE, EXPIRED, FUTURE) inside each grant, and the screen derives the effective permissions as the union of the ACTIVE ones (the property test proves it equals `effectivePermissions`). The session `mode` stays with the tenant selection answer. Change request: describe the grant and delegation items, and decide whether `mode` belongs in this answer.
- IAM-09 of the mockup has four tabs (Tổng quan, Số liệu, Tải liệu, Lịch sử) and a chart that no operation backs; they are not built, so the visual case compares the frame and the heading only.

No migration was needed. `membershipsAffectedByUnits` (the holders to notify when a unit moves) still costs about 0.2 s at p95 for a department of 259 units, because it compares every subtree grant with the changed units; it runs on a reorganisation, not on a read. Classify every PERSONAL column in the dictionary as data, not prose, so the test can read it.

- Legal hold and idempotency (M2f triage of 3f9dc42): the idempotency record of a command points at ONE audited resource (a tenant-plane command prefers one that a hold contains at completion time, else the first; a control-plane command takes the first, because the control role may not read holds). A hold placed later on a second resource of a multi-resource command does not protect the record; a TENANT hold and a hold on the first resource do. Reusing an expired key whose record is held sets the held record aside (its key becomes `retired:<id>`, everything else is kept) and starts a new record.
- Search projection (M2f triage of 3a7abe3): the scope of a search is judged on the CURRENT path of the owner unit (`left join organization_unit`), so a moved unit changes what its documents show at once; the `owner_unit_path` column of `search_document` is only a record of the path at projection time and could be dropped when the writer exists. ## M2f lane E2 design gaps (change request entries needed)
- The plan names `infra/**/*.yaml`; the files are JSON (`infra/**/*.json`): Node reads JSON without a dependency, and the repository has no YAML parser in its lockfile. The checks and the runbooks use the JSON names.
- Every infrastructure component is `PLANNED` with `restoreEvidence: null`: no restore test has been run, because no PostgreSQL primary and standby, object store, Keycloak, Temporal, collector, Redis, PowerSync or LiteLLM exists to restore. `npm run infra:check -- --require-entered <component>` fails until a real restore is recorded; the first stories of each component (listed by the check) wait for it.

## KERNEL-1 ST-KERNEL-071 (provider callback kernel) open points

- Scope (decision): the story has no operation, table or screen in the plan, so there is no controller. The kernel offers `verifyProviderCallback` (pure, `provider-signature.ts`), `defineStatusTable` / `reduceStatus` (pure, `provider-status.ts`) and `ProviderCallbackStore` (`packages/db/src/provider-callback-store.ts`): `receive` (verify, then write the inbox row), `track`, `applyEvent`, `markUncertain`, `resolveTask`, `openTasks`, `failEvent`. The provider controllers of NOT, OMNI and PAY (`receiveChannelWebhook` and the like) call `receive` and `applyEvent` in one tenant transaction, after they have found the tenant from the channel account and read the secret from the vault.
- Tables (decision): `provider_status_item`, `provider_status_history` (append-only) and `provider_reconciliation_task` are new in V1000 because the status of a send, its history and the reconciliation task have no generic table in V002 (`reconciliation_item` is PAY's, tied to a project and a contract). A module that already keeps a status column may use `reduceStatus` alone and keep its own history; the generic tables are for the modules that have none. The existing `integration_event_inbox` is reused as is; V1000 only adds a guard (identity of an event is fixed, a processed event stays processed).
- Monotonic rule (decision): a status table is an acyclic graph; a status is applied when it is later than the current one (skipping statuses is allowed), ignored as a repeat when equal, ignored as late when earlier, and ignored with a reconciliation task (`STATUS_CONFLICT`) when neither (FAILED after DELIVERED). Order comes from the graph, never from the provider's timestamp. The NOT, OMNI and PAY stories define their own tables (for example SENDING, UNCERTAIN, ACCEPTED, DELIVERED, READ, FAILED).
- Uncertain results (decision): `markUncertain` moves the item to UNCERTAIN, opens one `RESULT_UNCERTAIN` task (due after 24 hours) and writes the outbox event `provider.result_uncertain`; the module that owns the item subscribes and asks the provider. A late callback moves the item out of UNCERTAIN on its own, but the open task stays until a person closes it with `resolveTask` and a note (the status found at the provider; a status that is earlier or sideways is refused with 409 `STAGE_TRANSITION_DENIED`). Closing the task automatically when a callback resolves the uncertainty needs a worker identity for `resolved_by`; not done.
- Not done (needs the owners): the screens and operations to list and close reconciliation tasks (OMNI-11 shows the inbox and the reconciliation; no operation of the plan reads `provider_reconciliation_task`), the per-provider signing schemes (`TIMESTAMPED_HMAC_SHA256` and `BODY_HMAC_SHA256_PREFIXED` are the two shapes known so far; ZNS, WhatsApp, VNPAY and the signing providers add theirs), and an alert rule for `webhook_signature_failures_total` (OMNI telemetry asks for a warning above 10 failures in 5 minutes; the counter is emitted by `verifyProviderCallback`, the rule and its runbook belong with the OMNI story).

## ADM-1 ST-ADM-011 (delegation-of-authority matrix with resolver) open points

- Overlap in a draft (decision): `doa_rule` has an EXCLUDE constraint on the overlap of bands of one document type and unit, so a draft with an overlap cannot be stored. `createDoaMatrixDraft` and `updateDoaMatrixDraft` therefore answer 422 `DOA_MATRIX_INVALID` with `OVERLAP` where the overlap is written; `submitDoaMatrix` answers `GAP`, `NOT_FROM_ZERO`, `NOT_TO_INFINITY` (and `OVERLAP` again as a fence). - Four eyes beyond the author (decision, deepest governance): the table keeps `created_by` only. Migration V1301 adds `last_edited_by` (set by create, update and submit) and a CHECK that the approver is neither; the store checks both before the database does. A colleague who edited someone else's draft can therefore not approve it. BR-ADM-01 says "other than the maker"; whoever changed the content made it.
- A matrix without a rule (decision): `NO_RULES` blocks a submission and an approval, since an approved matrix with nothing in it would leave every document without an approver. The request schema already asks for at least one rule.
- Start date (decision): a version must start after the one in force (`NOT_AFTER_CURRENT`, 422 at the approval). A version dated between two published ones (back-dating, or inserting) is not supported; it needs a rule for what happens to approvals already pinned to the later version.
- Rule order: V1301 adds `doa_rule.position` (the row of the rule in the draft). The findings of a submission and of an approval name rules by that position (`rules[3].amount_min_vnd`), the row the administrator sees; reads return the rules in that order.

- `CXN-DOA-01`: the thresholds are the tenant's; the story is not DONE for the business owner until the pilot province regulation is entered as the first published version.

## PMT-1 (permits) open points
