## M2f lane B design gaps (change request entries needed)
- `acceptInvitation` is declared `x-plane: tenant` with permission `invitation.accept`, but the person who accepts holds an identity token and no tenant token yet (the invitation is what gives them a membership). It is implemented like `selectTenantContext`: an identity command (`@Public` plus the invitee guard), idempotent and audited by its own pipeline. Change the contract to say so (no tenant plane, no permission).
- IAM.md 3.3 answers an already used token with 409 `INVITATION_EXPIRED` (there is no used-invitation code); a token that names no invitation, a wrong secret and a token of another tenant are all the same 404 `RESOURCE_NOT_FOUND`, so the answer never says whether an invitation exists.
- The seat limit comes from the latest valid `license_revision`: `seats` for staff, `quota_json.guest_seats` for guest contractors (IAM.md 3.3 names `guest_seats` but SAS never defines the key). A tenant with no revision has no limit. Define the key in the licence claims.
- `MemberInvite` has no `reason`, so the audit row of `inviteMember` has none; without `initial_grants` the person receives the MEMBER role on their unit (what `session.self` needs), which no document states.
- The invitation message goes through the `InvitationMailer` port; the only adapter is the in-memory MOCK one until the OMNI email channel exists (R1), so no invitation mail leaves the system yet. The events `iam.membership.invited|activated|suspended|ended.v1` are not in the notification catalogue.
- The hourly job that expires pending invitations (IAM.md section 9) is not implemented here; an expired invitation is expired on its next acceptance attempt. It belongs to the scheduler of Task 12.
- The last-owner guard (BR-IAM-07) runs before the rank rule on purpose: no one outranks a TENANT_OWNER (rank 99), so after the rank rule it could never be reached.
- `EffectiveAccess` (openapi, `getMyEffectiveAccess`) has `additionalProperties: false` and free-form `grants` and `delegations_in` items, and no `mode` or permission list at the top: the API puts role, scope (units with breadcrumb, projects, contracts), permissions, window and `state` (ACTIVE, EXPIRED, FUTURE) inside each grant, and the screen derives the effective permissions as the union of the ACTIVE ones (the property test proves it equals `effectivePermissions`). The session `mode` stays with the tenant selection answer. Change request: describe the grant and delegation items, and decide whether `mode` belongs in this answer.
- IAM-09 of the mockup has four tabs (Tổng quan, Số liệu, Tải liệu, Lịch sử) and a chart that no operation backs; they are not built, so the visual case compares the frame and the heading only.

No migration was needed. `membershipsAffectedByUnits` (the holders to notify when a unit moves) still costs about 0.2 s at p95 for a department of 259 units, because it compares every subtree grant with the changed units; it runs on a reorganisation, not on a read. Classify every PERSONAL column in the dictionary as data, not prose, so the test can read it.

- Legal hold and idempotency (M2f triage of 3f9dc42): the idempotency record of a command points at ONE audited resource (a tenant-plane command prefers one that a hold contains at completion time, else the first; a control-plane command takes the first, because the control role may not read holds). A hold placed later on a second resource of a multi-resource command does not protect the record; a TENANT hold and a hold on the first resource do. Reusing an expired key whose record is held sets the held record aside (its key becomes `retired:<id>`, everything else is kept) and starts a new record.
- Search projection (M2f triage of 3a7abe3): the scope of a search is judged on the CURRENT path of the owner unit (`left join organization_unit`), so a moved unit changes what its documents show at once; the `owner_unit_path` column of `search_document` is only a record of the path at projection time and could be dropped when the writer exists. ## M2f lane E2 design gaps (change request entries needed)
- The plan names `infra/**/*.yaml`; the files are JSON (`infra/**/*.json`): Node reads JSON without a dependency, and the repository has no YAML parser in its lockfile. The checks and the runbooks use the JSON names.
- Every infrastructure component is `PLANNED` with `restoreEvidence: null`: no restore test has been run, because no PostgreSQL primary and standby, object store, Keycloak, Temporal, collector, Redis, PowerSync or LiteLLM exists to restore. `npm run infra:check -- --require-entered <component>` fails until a real restore is recorded; the first stories of each component (listed by the check) wait for it.

## KERNEL-1 ST-KERNEL-071 (provider callback kernel) open points

- Scope (decision): the story has no operation, table or screen in the plan, so there is no controller. The kernel offers `verifyProviderCallback` (pure, `provider-signature.ts`), `defineStatusTable` / `reduceStatus` (pure, `provider-status.ts`) and `ProviderCallbackStore` (`packages/db/src/provider-callback-store.ts`): `receive` (verify, then write the inbox row), `track`, `applyEvent`, `markUncertain`, `resolveTask`, `openTasks`, `failEvent`. The provider controllers of NOT, OMNI and PAY (`receiveChannelWebhook` and the like) call `receive` and `applyEvent` in one tenant transaction, after they have found the tenant from the channel account and read the secret from the vault.
- Tables (decision): `provider_status_item`, `provider_status_history` (append-only) and `provider_reconciliation_task` are new in V1000 because the status of a send, its history and the reconciliation task have no generic table in V002 (`reconciliation_item` is PAY's, tied to a project and a contract). A module that already keeps a status column may use `reduceStatus` alone and keep its own history; the generic tables are for the modules that have none. The existing `integration_event_inbox` is reused as is; V1000 only adds a guard (identity of an event is fixed, a processed event stays processed).
- Monotonic rule (decision): a status table is an acyclic graph; a status is applied when it is later than the current one (skipping statuses is allowed), ignored as a repeat when equal, ignored as late when earlier, and ignored with a reconciliation task (`STATUS_CONFLICT`) when neither (FAILED after DELIVERED). Order comes from the graph, never from the provider's timestamp. The NOT, OMNI and PAY stories define their own tables (for example SENDING, UNCERTAIN, ACCEPTED, DELIVERED, READ, FAILED).
- Uncertain results (decision): `markUncertain` moves the item to UNCERTAIN, opens one `RESULT_UNCERTAIN` task (due after 24 hours) and writes the outbox event `provider.result_uncertain`; the module that owns the item subscribes and asks the provider. A late callback moves the item out of UNCERTAIN on its own, but the open task stays until a person closes it with `resolveTask` and a note (the status found at the provider; a status that is earlier or sideways is refused with 409 `STAGE_TRANSITION_DENIED`). Closing the task automatically when a callback resolves the uncertainty needs a worker identity for `resolved_by`; not done.
- Not done (needs the owners): the screens and operations to list and close reconciliation tasks (OMNI-11 shows the inbox and the reconciliation; no operation of the plan reads `provider_reconciliation_task`), the per-provider signing schemes (`TIMESTAMPED_HMAC_SHA256` and `BODY_HMAC_SHA256_PREFIXED` are the two shapes known so far; ZNS, WhatsApp, VNPAY and the signing providers add theirs), and an alert rule for `webhook_signature_failures_total` (OMNI telemetry asks for a warning above 10 failures in 5 minutes; the counter is emitted by `verifyProviderCallback`, the rule and its runbook belong with the OMNI story).

## KERNEL-1 ST-KERNEL-070 (idempotent file-import framework, kit K6) open points

- Scope (decision): the story has no operation, table or screen in the plan, so there is no controller. The kernel offers `planFileImport` and the format types (`packages/kernel/src/file-import.ts`, pure); the db package offers `FileImportStore.run` (claim the file, quarantine, claim rows, apply, open items; `totals`, `quarantined`, `list`, `find`) and `FileImportItemStore` (`list`, `resolve`, `reassign`), and V1002 adds `file_import`, `file_import_row`, `file_import_quarantine`, `file_import_reconciliation_item`. How a module plugs a format in: `docs/file-import.md`. No concrete layout is built (the Treasury layout waits for the anonymised samples, R-PAY-04).
- Reference adapter: the reference implementation is the test adapter in `packages/db/test/file-import-store.test.ts` (CSV, project check in `examine`, a write in `apply`, an `AMOUNT_MISMATCH` difference with an owner). PAY, DIS, CAP and BID copy that shape.
- Reading of AC-ST-KERNEL-070-1 (decision): "a file of 120 rows, 117 load, 2 quarantined, 1 amount mismatch" is read as 120 lines of CSV with the header, so 119 data rows: 117 loaded (the mismatching row is one of them, with its item) and 2 quarantined (UAT-NFR-OPERABILITY-06: "117 dòng nhận, 2 quarantine, 1 hạng mục đối soát"). A row with a difference is applied and has an open item; it is not held back. If PAY wants a mismatching amount held out of the ledger until the item is resolved, `examine` can refuse it with its own code, or `apply` can write it with a status that the module's totals leave out; the core counts it as applied.
- Idempotency (decision): a file is identified per tenant and connector by the SHA-256 of its bytes (`file_import_file_uq`, unique unless the try FAILED); a row by tenant, connector and business key (`file_import_row_key_uq`) with a row hash of its normalised fields. Same key and same hash is a repeat (skipped, counted); same key and another hash is a conflict (the original is untouched, one `DUPLICATE_CONFLICT` item per connector and key, joined by later conflicts). A correction of an already applied row is therefore a person's decision on the item, not an overwrite. The file claim is an `INSERT ... ON CONFLICT DO NOTHING`, so of two concurrent imports one waits for the other and answers `ALREADY_IMPORTED`; a rolled back winner lets the waiting one proceed (tested).
- One transaction per file (decision, limit): a file is judged and applied in one tenant transaction, at most 5,000 rows (the limit of `readTabularFile`), so a defect leaves nothing behind and the same file can be tried again. This is the same limit as ST-MDM-006. A larger file needs a chunked variant (stage the plan, then apply in chunks with a resumable cursor on `file_import`); not built, because the plan's 120-row scenarios and the Treasury daily statement fit, and chunking changes the all-or-nothing guarantee. Rows are claimed in the order of their keys so two files with the same keys in opposite orders do not deadlock (tested).
- Owner and due date (decision): every item is created with `owner_membership_id` (NOT NULL, foreign key to `membership`) and `due_at`. `ownerFor` of the adapter names the officer; an owner who is not an active member falls back to the `fallbackOwnerId` of the run, which must be an active member (422 `owner_membership_id` otherwise). Default time to settle is 3 days (`DEFAULT_ITEM_DUE_SECONDS`); the run and each difference can set another. A handover (`reassign`) keeps the due time and needs the version. The rule that chooses the owner (project officer, treasury reconciliation officer) belongs to each module; the PAY rule needs the business owner's confirmation.
- Not done, needs the owners: (a) who may start an import, read the quarantine, resolve or hand over an item: the permissions, scopes and audit rows are the controllers' (PAY-13 and the like); the stores only record the people; (b) the notification to an owner when an item opens (the outbox event `file_import.difference_opened` carries the item id, owner and due time; NOT subscribes), and the escalation of an overdue item (PAY's `reconciliation_item.issue_id` creates an ISS issue; a scheduler job over `file_import_reconciliation_item` with `dueBefore = now` is not written, nor is its alert rule); (c) retention of the four tables: they hold business keys, hashes and masked previews, no personal data by design, and nothing deletes them; the ADM retention rule for them is not defined; (d) the Temporal workflow of NFR-OPERABILITY-06 ("Workflow import trên Temporal") is not built; `FileImportStore.run` is one transaction and can be the body of an activity; (e) no operation of the contract reads `file_import`, so there is no import report screen; the data is there (`find`, `list`, `quarantined`, `totals`).
- PAY-006 and the other consumers (decision to confirm): PAY's `treasury_import`, `treasury_import_row` and `reconciliation_item` (V002) are PAY's tables, tied to a project and a contract. They can stay as the module's own record (written in `apply`, with `import_id` from the context pointing at `file_import`), or PAY can drop `treasury_import` for `file_import` and keep only `treasury_transaction`. The framework is built so that the second is cheaper; the first loses nothing. PAY's `reconciliation_item` (project, contract, amount columns, `EXPLAINED` and `WRITTEN_OFF_APPROVED` states with approval) is richer than the generic item and stays PAY's; its adapter can create it from the `Difference` it returns, or use the generic item and link it.
- MDM bulk import (decision, not refactored): `master-import-store.ts` (636 lines, ST-MDM-006) is left as it is. Its unit is a reviewed batch, not a file: stage, dry run, ATOMIC or PARTIAL mode, change requests with four-eyes, publication of the batch as one, a hash check at stage and at apply. None of those is a file-import concern, and it keeps its own `file_sha256` on `master_import_batch` and its row errors in `errors_json`. Putting it on the core would mean either quarantining rows that the batch screens already show, or changing the ATOMIC guarantee (the core claims a key once and never replays it), so the work is larger than the duplication it removes and it would reopen a reviewed, tested slice. What is already shared: the tabular reader (`readTabularFile`, lines and XLSX dates), which the core's `sourceRowsOfTable` also uses, and the file hash. Revisit when MDM-24 connector files (`NATIONAL_PIM_FILE`, `BUDGET_CODE_FILE`) get a real feed: those are plain file imports and use the core.
- Cursor (decision): `cursorScope` is opt-in. With it the connector must be `ACTIVE`, a read file sets `last_file_sha256` and `last_success_at`, an unreadable file sets the connector `FAILED` with `last_error_code` (only the reset of MDM-24 starts it again, as MDM-24 defines) and the cursor row is locked so imports of one connector take turns. A tenant without that row is not touched.
- Shared files touched with small edits: `packages/kernel/src/index.ts`, `packages/db/src/index.ts`, `packages/db/test/retained-history-grants.test.ts` (the four tables), this file. Two db suites outside this story were red when run (`rls-catalog.test.ts`: `project_stage_change` has a non-standard policy set and `issue`, `outgoing_document_event`, `project_stage_change` have `_id` columns without a `(tenant_id, column)` index); none of the four new tables is in those reports.

### ST-CAP-001 (appropriation register by origin, slice CAP-1)
- ST-CAP-001 (decision, table): `appropriation` came from the generated schema (V002); `V1360__cap1_appropriation_register.sql` adds what the register relies on: REJECTED in the status CHECK, amount above zero, a trimmed authority of 2 to 300 characters, years 1990 to 2100, source year = plan year unless CARRYOVER, a revision chain (revision 1 has no `supersedes_id`, a later one has), the approver required once the row leaves DRAFT, foreign keys of both documents to `document`, a unique decision line `(document, fund source version, program, year, origin, level)` and one live successor per appropriation, a BEFORE UPDATE guard (content is never edited, REJECTED and SUPERSEDED are final, the state machine, the approver is final) and no DELETE for the application role.
- ST-CAP-001 (decision, allocated total): `allocated_total_vnd` can change only inside a transaction that raised `app.cap_allocation_write = 'on'` (`set_config(..., true)`) and only on a PUBLISHED row. `CapAppropriationStore.decide` raises it for the one case of this story (a revision inherits the allocated total of the appropriation it replaces); the allocation command of ST-CAP-002 must do the same, lock the appropriation rows `FOR UPDATE` in the order of their ids, and never write the column otherwise. No API body can carry it (the allowlist answers 400 `FIELD_NOT_ALLOWED`).
- ST-CAP-001 (decision, revision): a revision is a new DRAFT row with `supersedes_id`, `revision + 1`, the same fund source ENTRY (a newer version of it is fine), program entry, plan year, source year, origin and level. It is refused below the allocated total at registration (nothing is written, 422 `APPROPRIATION_BELOW_ALLOCATED`) and again at the decision under the row locks. Publishing it supersedes the old row, moves the `allocation_line` rows and the allocated total to the revision, and posts to `capital_ledger_entry`: a REVERSAL of the old APPROPRIATE (`reversal_of_id`) and a new APPROPRIATE, so the net of the appropriation entries is always the amount in force. The first publication posts one APPROPRIATE. Reconcile (`capital.balance-reconcile`) only PUBLISHED rows: a SUPERSEDED row keeps the allocated total it had when it was replaced, as history.
- ST-CAP-001 (decision, decisions): `decideAppropriation` approve publishes at once (DRAFT to PUBLISHED, the APPROVED state of the schema stays unused); reject ends the draft (new status REJECTED, frees the decision line); `return` has no meaning for a draft that cannot be edited and is 422 `VALIDATION_FAILED` (`decision`). The registrant never decides (403 `SELF_APPROVAL_DENIED`, also a DB CHECK). The master data (fund source, program) and the documents are judged again at the decision.
- ST-CAP-001 (decision, rules): the fund source must be a FUND_SOURCE entry in force today that adds to the others: a `relation = SUBSET_OF` source (CTMTQG) is refused with 422 `SUBSET_SOURCE_NOT_ADDITIVE` (it is part of its parent; its amount is tracked on the allocation line, `ctmtqg_subset_vnd`, BR-CAP-03). A decision document must exist in the tenant and have an `effect_status` of PENDING, EFFECTIVE or CORRECTED (else 422 `DECISION_REQUIRED`; a missing `decision_document_id` is the same code through `FIELD_PROBLEMS`). A CARRYOVER needs its extension document (422 `EXTENSION_DOCUMENT_REQUIRED`), `extended_to` (not before 1 January of the plan year) and a source year before the plan year; the carry-over fields on any other origin are 422. A plan year whose `fiscal_year_control` row is LOCKED takes no capital (409 `FISCAL_YEAR_LOCKED`; ST-CAP-008 owns the table). New code `APPROPRIATION_DUPLICATE` (409) registered in `error_codes.json` for the unique decision line; a second live revision is 409 `REVISION_PENDING_EXISTS`.
- ST-CAP-001 (decision, money): amounts are strings of whole VND (`requirePositiveAmount` with scale 0, at most 24 digits, nothing is rounded); sums and remaining amounts are computed by PostgreSQL `numeric` or by BigInt in the web, never by a float. `appropriation` is not a declared ledger table (it is no `*_balance`); the ledger declarations of `capital_ledger_entry` (V002) are used as they are. The web types an amount in millions of dong and sends exact VND; only the decimal mark of the language is accepted (a point is a grouping mark in Vietnamese, so "10.000" is refused instead of being read as ten), and the line "Sẽ ghi N đồng" shows the exact dong before sending.
- ST-CAP-001 (decision, scope): the register belongs to no unit: `capital.appropriation.manage`, `capital.appropriation.approve` and `capital.read` are judged as tenant permissions (the contract says `tenant`). The list returns DRAFT and PUBLISHED rows (the register in force and what awaits a decision), newest first; the decision document is shown by its symbol and date, never its title.
- ST-CAP-001 (screens): CAP-16 is the book (filters, pinned fund and year columns, millions with the exact dong on the cell, Con lai, totals of the published lines, register, revise, approve and reject with a reason of at least 5 characters); CAP-04 is the tree category / fund source / origin of the published lines with the validity and the ODA on-lending, CTMTQG explained and never added; CAP-14 shows CENTRAL_SUPPORT and REVENUE_INCREASE as groups of their own. ## ISS-3, ISS-4, ISS-5 (ST-ISS-003 verification and closure, ST-ISS-004 escalation, ST-ISS-005 intake) decisions and open points

- ST-ISS-003 (decision, V1063): the limit of extensions (2) and the window of a reopening (30 days) are working assumptions of the tenant rules (R-ISS-01) held once in code (`ISSUE_MAX_EXTENSIONS`, `ISSUE_REOPEN_WINDOW_DAYS` of `iss-issue-closure.ts`, sent to the screens in the issue read as `extensions` and `reopen_window_days`). Move the numbers to rule data when the pilot tenant signs them.
- ST-ISS-003 (decision, who "asks" for an extension): the contract has one command, `extendIssueDeadline` (`issue.extend`), and no command that records a request. The person who asks is the one who answers for the deadline, the assignee (UAT-AC353 names u.cv.hd, the handler, as the requester): the assignee cannot grant the extension of their own issue (403 `SELF_APPROVAL_DENIED`). The event kind `EXTENSION_REQUESTED` of the design stays unused until the contract gets a command to propose an extension (a contract change for the orchestrator: `requestIssueExtension`, `issue.work`, writes `EXTENSION_REQUESTED`); then the approver must also differ from whoever proposed.
- ST-ISS-003 (decision, "adds the days on the working calendar"): one extension adds at most the resolution time of the policy of the issue counted on the working calendar of that policy (`IssSlaDeadlines.addMinutes`), from the later of the present deadline and now; the new deadline must be later than the present one and in the future (422 `VALIDATION_FAILED` `new_due_at`). An extension never clears `overdue_since`; when the old deadline had passed and the job had not noticed yet, the extension writes it first (the deadline that was missed).
- ST-ISS-003 (decision, independence): the closer is never the assignee, whatever the policy says: `issue_verifier_chk` of the generated schema is unconditional, so `require_independent_verifier = false` is stored and shown but cannot let an assignee close their own issue (403 `SELF_APPROVAL_DENIED`). The evidence the policy asks for is judged at the request for verification (422 `EVIDENCE_REQUIRED`, documents of the tenant scanned clean, at most 20) and again by the database: the trigger `issue_guard` refuses CLOSED without a VERIFICATION_REQUESTED event, and without evidence in it when the policy asks. `closeIssue`, `reopenIssue`, `requestIssueVerification` check the state before the version, so a command sent again under a new key after it succeeded is 409 `ISSUE_STATE_INVALID` (UAT-AC397); the same key answers the first body (the interceptor).
- ST-ISS-003 (decision, giving the result back): the verifier refuses the result with `assignIssue` (PENDING_VERIFICATION to ASSIGNED), which now needs the reason (`note`) and withdraws `resolved_at`; the event is REASSIGNED with `outcome: VERIFICATION_REFUSED`. The person who refuses holds `issue.assign`, not necessarily `issue.close`. Closing resolves the open escalations of the issue; a reopening clears the closure (`closed_at`, `closed_by`, `verifier_id`, `issue_closed_fields_chk`) and begins the escalation again (`escalation_level` back to 0).
- ST-ISS-003 (not done): the maker-checker matrix of the authorization tests (`APPROVER_COMMANDS`) lists approvals by "who made the object"; closing and extending are independent of the ASSIGNEE, which the matrix does not model, so they are covered by their own tests (store, HTTP, browser) and not added there. Evidence is typed as document version ids (the contract has no upload for an issue, see ST-ISS-002 not done, photos). The reopening is a screen of ISS-07; the weekly matrix (ISS-06, ISS-08) is not built.
- ST-ISS-004 (decision, levels): ISS.md 3.2 and UAT-AC352 give escalation levels 1 (unit), 2 (the person in charge, at `escalate_l2_pct`) and 3 (the task force, at `escalate_l3_pct`), while the acceptance text of the plan speaks of "level 1 at 100 percent and level 2 at 150". The module document wins: the job raises level 2 to the owner unit at 100 percent (the leaders of the project by `project_accountability` are the named recipients of the notification) and level 3 to the task force at 150 percent; level 1 is raised by hand only (`escalateIssue`, to any unit of the tenant, the owner unit by default). A manual escalation must be to a level above the one the issue has reached (422 `ESCALATION_LEVEL_INVALID`), levels 1 and 2 name a unit and level 3 an active task force that answers for the issue (422 `TASK_FORCE_NOT_ACTIVE` for a dissolved one, 422 `VALIDATION_FAILED` `task_force_id` for an unknown or unrelated one), and the issue must be ASSIGNED or IN_PROGRESS (the only edges to ESCALATED).
- ST-ISS-004 (decision, thresholds): a threshold at or above 100 percent is counted from the current `due_at` (an extension moves it): 100 percent is the deadline, 150 percent is `resolve_hours` * 0.5 working hours after it; a threshold below 100 percent is counted from `opened_at`. The working time is that of the policy calendar and the ISS window 07:30-17:00 (`addWorkingTime`); a year without a published calendar is never guessed: the level waits for a later pass (`withoutCalendar`). `overdue_since` is the missed deadline itself (`due_at`), written once with the timeline event `SLA_BREACHED` by the first pass after it; the version of the issue does not move for it.
- ST-ISS-004 (decision, states): the job looks at OPEN, ASSIGNED, IN_PROGRESS, ESCALATED and REOPENED issues, not at an issue that waits for its verification (the delay is the verifier's, not the handler's). The escalation of an OPEN or REOPENED issue is recorded and raises `escalation_level`, but the status stays (the machine has no edge from them to ESCALATED); the acceptance puts an ESCALATED issue back to IN_PROGRESS and leaves any other status alone. - ST-DOC-010 (decision, aggregate status): the document is DELIVERED when one row is DELIVERED or ACKNOWLEDGED (a receipt on a SENT row delivers it at the instant of the receipt) and ACKNOWLEDGED when at least one recipient must acknowledge and all of them have (`document_distribution.acknowledgement_required`, a column V1223 adds: the design says "mandatory recipients" but the table had no column for it; default true). Both moves, their history rows and `doc.delivered.v1` / `doc.acknowledged.v1` happen in the command that caused them, once. A resend finds the row (unique per document, lower-cased recipient name and channel) and writes nothing; `retryDocumentDistribution` sends a FAILED row again.
- ST-DOC-010 (decision, read): there is no list operation for the distributions of a document, so `getOutgoingDocument` carries `distributions` (an allowlist of fields, at most 500 rows), `renders_watermarked` and `unconfirmed_override_reason`. The response of that operation is an untyped object, so no contract change was needed. A paged `GET /outgoing-documents/{id}/distributions` is a better read once documents have many recipients.
- ST-DOC-010 (contract gaps for the orchestrator): (1) `DocDispatch.recipients` items are `type: object` without members, so the generated type admits no member and the typed client takes one cast (`recipientBody` in `apps/web/src/screens/doc/distribution/hooks.ts`); the members read are `kind`, `name`, `code`, `unit_id`, `channel` (INTERNAL, EMAIL, PAPER_HANDOVER) and `acknowledgement_required`. (2) `issueOutgoingDocument` can answer 503 `PROVIDER_UNAVAILABLE` and 403 `SCOPE_DENIED`, `dispatchOutgoingDocument` 422 `RECIPIENT_INVALID` with a reason member; neither is in `x-error-codes` of the operation. (3) `doc.delivered.v1` and `doc.acknowledged.v1` are announced by the issue (with `distribute_now`), the dispatch, the receipt and the retry, whichever moves the document.
- ST-DOC-010 (job, not scheduled): `recheckIssuedRevocation` (`revocation-recheck.ts`, the `doc.revocation-recheck` job of the design) asks again about the documents in force whose latest verification is older than a day or not good, stores the new verification and raises `DOC_ISSUED_SIGNATURE_REVOKED`; like the register jobs it is a function over the transaction of one tenant that the platform scheduler has to call once per tenant (no scheduler registers DOC jobs yet). It also verifies only the sealed file; the long-term validation (DSS and document timestamp, `ISSUED_LTV`) is not built.
- ST-DOC-010 (not done): the metric `doc_issue_latency_seconds` is the time from the seal to the issue (a gauge: the sink has no histogram); no email delivery receipts, no recall notice to recipients (ST-DOC-019), no incoming side of the internal channel (the inbox of the unit is only the row).
- ST-DOC-010 (tests): the chain test of ST-DOC-008 (`issue-requests.test.ts`, UAT-AC410) now issues through the real command (`FlowWorld.issueSealed`); the isolation suite has a distribution of each tenant (`DOCUMENT_FIXTURES.distributionId`) and the authorization matrix a distribution of tenant A (`distributionId`). Browser: `apps/web/e2e/doc-issue-flows.spec.ts` (6 flows, users `docIssuer`, `docLegal`, `docIssueOnly`, `docReader`); the stack answers "not revoked" for the test authority (`DOC_REVOCATION` override) and keeps the real unconfigured email adapter.

## PMT-1 (ST-PMT-003: permit exemption) open points

- ST-PMT-003 (decision, who proposed): the design says the approver is not "the proposer" without defining the proposer. A permit has no proposer column, so the proposer is the person who created the permit (opened the dossier or added the permit) and whoever last changed it (`updated_by` before the exemption): neither can declare its exemption (403 `SELF_APPROVAL_DENIED`, also held by the trigger of `V1182` for every role but the owner). A leader who recorded an unrelated milestone is therefore not an approver of that permit either; the cost is accepted for the stricter reading of BR-PMT-04. Whether the people who recorded earlier milestones count is not decided by the design.
- ST-PMT-003 (decision, type): the type version the permit was written under decides `exemption_allowed` (422 `EXEMPTION_NOT_ALLOWED`); the conditions of the construction law [CXN-EXE-02] stay data of the type, not code. A planned or submitted permit can be exempted, any other status is 409 `PERMIT_STATE_INVALID`; a type that already has a current permit in the dossier is 409 `PERMIT_ALREADY_CURRENT`.
- ST-PMT-003 (what it writes): status EXEMPTED with the trimmed basis (at most 2000 characters, `permit_exempt_basis_chk`) and the decision document (readable, not infected), a DECISION milestone dated today that names the document, the readiness of the dossier counted again (an exemption covers its type already), the audit row `pmt.permit_exempted` (ids and states, not the text of the basis) and `pmt.permit.exempted.v1`. The gate evaluation (`evaluatePermitGates`, requirement VALID_OR_EXEMPT) is a later story; the readiness count and the PMT-02 summary already treat EXEMPTED as covering.
- ST-PMT-003 (scope, web): `permit.exempt` is held by the leader of the unit tree or project (not whole-tenant), so the command acts inside the grant like the other permit commands. PMT-02 offers the form to someone who holds the permission for a PLANNED or SUBMITTED permit of a type that allows it; the server still refuses the proposer. Fixture users `permitLeader` and `permitProposerLeader`; browser flow `apps/web/e2e/pmt-exemption-flows.spec.ts` (3 tests).
- ST-PMT-003 (not done): the exemption of a gate (`grantPermitGateWaiver`, PMT-06 second half) and the revocation of an exemption are other stories; the decision document is a version id typed on the form like the other PMT scans (no document picker).
